## 1. システム概要

CoreFusion は、ノード管理、サブスクリプション配信、顧客管理、請求、証明書、チェーン プロキシを備えた VLESS、VMess、Trojan、Shadowsocks、Hysteria2、TUIC などをサポートするマルチプロトコル プロキシ管理パネルです。

### 1.1 コア機能

| モジュール | 説明 |
|--------|-------------|
| マルチプロトコル | VLESS、VMess、Trojan、Shadowsocks、Hysteria2、TUIC、WireGuardなど。 |
| マルチコア | Xray コアおよび sing-box (Hysteria2/TUIC およびその他の QUIC プロトコルは sing-box で実行されます) |
| マルチノード | 5 つのノード タイプ: スタンドアロン、ミラー、アクティブ/スタンバイ、連鎖エントリ、連鎖出口 |
| 定期購入の配信 | 複数のサブスクリプション形式、エンドポイント、形式管理 |
| 請求 | プラン テンプレート、リチャージ カード、残高、注文、再販業者手数料 |
| 証明書 | Let's Encrypt発行、DNS-01/HTTP-01検証、証明書配布 |
| チェーンされたプロキシ | マルチ出口ロードバランシング、外部ノード登録、チェーンルーティング |
| トラフィック割り当て | ノードごとの月次トラフィック監視、自動一時停止、ログのリセット |
| ポータル | ビジュアルポータルエディター、多言語、カスタムテンプレート |
| 通知 | 電子メールと Telegram、テンプレートとブロードキャスト |

### 1.2 アーキテクチャ

- **バックエンド**: Go、gRPC
- **フロントエンド**: Vue 3 + Element Plus
- **データベース**: SQLite (デフォルト) / MySQL / PostgreSQL
- **プロキシ**: Caddy / Nginx リバース プロキシ
- **パネル ポート**: セットアップ ウィザードによって割り当てられます (デフォルトではランダムな空きポート。8080 が一般的な選択です)
- **エージェント gRPC ポート**: デフォルトは 18443

## 2. インストール

### 2.1 サポートされる環境

| アイテム | サポート |
|------|---------|
| 分布 | Debian / Ubuntu、RHEL / CentOS / Rocky / AlmaLinux / Fedora、Alpine、Arch、openSUSE |
| CPUアーキテクチャ | 公式バイナリ: `amd64`、`arm64`。ソース ビルドは `armv7`、`armv6`、`386`、`ppc64le`、`s390x`、`riscv64`、`loong64` もサポートします |
| サービスマネージャー | systemd (推奨); systemd のないコンテナまたは他の環境では `nohup` にフォールバックします |
| メモリ/ディスク | ≥ 1 GB / ≥ 10 GB (データベース、証明書、ログ、コア バイナリはデータ ディレクトリに存在します) |
| パネルポート | セットアップ ウィザードで選択 (デフォルトではランダムな空きポート。`8080` などで問題ありません) |
| エージェント gRPC | デフォルトでは`18443` |

ランタイム外部コマンドは、インストーラーによって自動的にインストールされます (`scripts/install.sh` およびパネルによって生成されたエージェント インストール スクリプト。`--no-deps` / `CF_SKIP_DEPS=1` はスキップします)。

| 目的 | パッケージ |
|---------|---------|
| ファイアウォール / レート制限 / 同時実行マーキング | `nftables` (`nft`) |
| トラフィックシェーピング、リンク、ソケット | `iproute2` (`tc` / `ip` / `ss`) |
| NFT が利用できない場合のフォールバック | `iptables` (EL8+ では `iptables-nft`、EL7 では `iptables`) |
| 接続追跡 | `conntrack-tools` (`conntrack`) |
| `nf_conntrack` / `ifb`をロードする | `kmod` (`modprobe` / `lsmod`) |
| プロセスの検出とクリーンアップ | `procps` (`pgrep` / `pkill`) |
| ポートチェック/DHパラメータ | `lsof` / `openssl` |
| プロキシユーザーの作成 | `shadow-utils` (Debian `passwd`、Alpine/Arch `shadow`) |
| ダウンロードとアーカイブ | `curl` / `ca-certificates` / `tar` / `gzip` / `xz` |

> `nft` / `tc` がない場合は、レート制限とファイアウォール機能にのみ影響します。パネルはまだ開始されています。
> 最初に `--cpu-info` を実行して、環境がどのように検出され、どのパッケージが欠落しているかを確認します。

### 2.2 1 行インストール (推奨)

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh -o install.sh
sudo bash install.sh
```

または、直接パイプします (インタラクションや追加のフラグは必要ありません)。

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash
```

スクリプトは次のことを行います。

1. ディストリビューション、CPU アーキテクチャ、libc を検出し、基本パッケージとランタイムの依存関係をインストールします。
2. GitHub リリースから `corefusion-linux-<arch>` をダウンロードし、一致する `.sha256` で検証します。
3. Install to `/opt/corefusion` and create `data/{sqlite,certs,logs,runtime}`;
4. Write only a placeholder `.env` with `SAFE_PATHS=data` — no database config — so the first start enters the setup wizard (the full `.env` is generated by the wizard);
5. systemd サービスをインストールして開始します (または、systemd が使用できない場合は `nohup` で実行します)。
6. 準備ができるまで待ってから、セットアップ URL、トークン、およびディレクトリ パスを出力します。

出力例:

```text
==================================================================
 CoreFusion installation complete
------------------------------------------------------------------
 Install dir : /opt/corefusion
 Data dir    : /opt/corefusion/data
 Binary      : /opt/corefusion/corefusion
 Logs        : journalctl -u corefusion -f
------------------------------------------------------------------
 Setup wizard : http://<server-ip>:<random-port>/init?init_token=<token>
 Setup token  : <token>
 Valid for    : 2 hours (see startup log)
 Note         : the token is shown once; after setup this port closes and the panel switches to its normal port.
==================================================================
```

If the panel only listens on `127.0.0.1` (for example behind a reverse proxy), the script prints an SSH tunnel command instead of an unreachable URL.

> トークンを紛失しましたか? Read the startup log again: `journalctl -u corefusion -n 50 --no-pager`
> (without systemd: `tail -n 50 /opt/corefusion/data/logs/panel.log`).

### 2.2.1 多言語出力

インストーラーには、簡体字中国語、英語、ペルシア語 (فارسی)、ロシア語 (Русский) の 4 つの UI 言語が含まれています。システム `LANG` を自動検出するか、明示的に選択できます。

```bash
# English
sudo bash install.sh --lang en

# Persian via environment variable
sudo CF_LANG=fa bash install.sh

# Pass options through a pipe
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash -s -- --lang ru
```

サポートされている値: `zh` / `en` / `fa` / `ru`; `--lang=ru` is also accepted.サポートされていない明示的な値は、使用可能な言語のリストでは失敗します。

### 2.3 バージョンの固定 / ミラー / オフライン インストール

```bash
# Pin a version
sudo bash install.sh --version v0.13.1

# GitHub download mirror (used as a URL prefix)
sudo bash install.sh --mirror https://ghproxy.net --version latest

# Use a local binary (offline / intranet / pre-built)
sudo bash install.sh --local ./dist/corefusion-linux-arm64

# Explicit target architecture
sudo bash install.sh --arch arm64 --local ./corefusion-linux-arm64
```

> `--version` がない場合、スクリプトは GitHub リリース リストの最新のエントリを使用します。
> ほとんどのリリースはプレリリースであるため、`/releases/latest` エンドポイントは使用されません。
>
> 公式リリースでは `amd64` / `arm64` のみが提供されます。他のアーキテクチャの場合は、`--source` または `--local` とクロスコンパイルされたバイナリを使用してください。

### 2.4 ソースからのビルド

```bash
sudo bash install.sh --source --version v0.13.1
```

`--source` はリポジトリのクローンを作成し (スクリプトがリポジトリ内にある場合は既存のチェックアウトを使用し)、`make panel` を実行します。ツールチェーンのバージョンは環境ごとに選択されます。

| 依存関係 | 選択 |
|------------|-----------|
| 行く | `go.mod` の `toolchain` / `go` から読み取ります (現在 **Go 1.27+**)。システムのバージョンが古すぎる場合、一致するツールチェーンが `<install-dir>/.toolchain` にダウンロードされます |
| ノード | **デフォルトではノード 22 LTS** (Vite には 18 以上が必要です)。必要に応じて、一致する公式ビルドがダウンロードされます |
| ノード (glibc < 2.28) | `unofficial-builds` glibc-217 ビルドを使用します (CentOS 7 など) |
| ノード（アルパイン/イガイ） | `nodejs` / `npm` ディストリビューションを使用 |

オーバーライド:

```bash
# Force Go / Node versions
sudo CF_GO_VERSION=1.27.5 CF_NODE_MAJOR=22 bash install.sh --source

# Go toolchain mirror (default https://go.dev/dl)
sudo CF_GO_MIRROR=https://golang.google.cn/dl bash install.sh --source
```

手動ビルド (開発/デバッグ):

```bash
git clone https://github.com/qist/corefusion.git
cd corefusion

# Frontend + panel for the current architecture; the frontend is embedded via go:embed
make panel

# Cross-compile
make panel-linux-amd64
make panel-linux-arm64
```

> `go build ./...` はバイナリを生成しません。パネルを構築します
> `go build -o corefusion ./cmd/corefusion/`または`make panel`。

### 2.5 インストーラーのフラグ

| 旗 | 説明 |
|------|-------------|
| `-d, --dir <PATH>` | インストールディレクトリ、デフォルト `/opt/corefusion` |
| `-v, --version <TAG>` | パネルのバージョン、例: `v0.13.1`;デフォルト `latest` |
| `--binary` | GitHub リリース バイナリを使用します (デフォルト) |
| `--source` | ソースからビルドし、一致する Go / Node を準備する |
| `--local <FILE>` | ローカルバイナリを使用する(オフラインインストール) |
| `--arch <ARCH>` | ターゲットアーキテクチャ: `amd64` / `arm64` / `armv7` / `armv6` / `386` / `ppc64le` / `s390x` / `riscv64` / `loong64` |
| `--mirror <URL>` | GitHub ダウンロード プレフィックス、例: `https://ghproxy.net` |
| `--repo <URL>` | ソースリポジトリ、デフォルトは `https://github.com/qist/corefusion.git` |
| `--ref <REF>` | ソースブランチ/タグ;デフォルトは `--version`、それ以外の場合は `main` |
| `--no-deps` | システム依存関係のインストールをスキップする |
| `--no-start` | 起動せずにサービスファイルをインストールして書き込みます |
| `--cpu-info` | 環境の検出と不足している依存関係を出力して終了します。 |
| `--lang <LANG>` | 出力言語: `zh` / `en` / `fa` / `ru` (デフォルト: システム `LANG`) |
| `--uninstall` | サービスを停止し、プログラムを削除します（データと`.env`は保持します）。 |
| `--purge` | `--uninstall` では、データ ディレクトリと `.env` も削除します |

> 公式リリースには、`amd64` / `arm64` バイナリのみが同梱されます。他のアーキテクチャには `--source` が必要です。
> それ以外の場合、ダウンロードは 404 を返します。

関連する環境変数:

| 変数 | 目的 |
|----------|---------|
| `CF_GO_VERSION` | ソースビルドに必要な Go バージョンをオーバーライドする |
| `CF_NODE_MAJOR` | ノードのメジャー バージョン (デフォルトは 22) をオーバーライドします。 |
| `CF_GO_MIRROR` | Go ツールチェーンのダウンロード ミラー |
| `CF_SKIP_DEPS` | 依存関係のインストールをスキップするには、エージェントのインストール スクリプトで `1` に設定します。 |
| `CF_LANG` | インストーラーの出力言語をオーバーライドします (`--lang` と同じ) |

### 2.6 ディレクトリのレイアウト

```text
/opt/corefusion/
├── corefusion                 # panel binary
├── corefusion.bak             # previous version (when upgrading)
├── .env                       # environment file (0600, generated by the setup wizard)
├── .env.secret                # encryption key file (0600, generated on first start)
├── .toolchain/                # Go / Node downloaded for source builds
└── data/                      # data directory (SAFE_PATHS)
    ├── sqlite/app.db          # default SQLite database
    ├── certs/                 # certificates and keys
    ├── logs/                  # runtime logs (without systemd)
    ├── runtime/               # core runtime config and state
    ├── binaries/              # downloaded xray / sing-box cores
    └── proxy/                 # proxy (Caddy/Nginx) sites and config
```

> インストーラーは、`sqlite/`、`certs/`、`logs/`、および `runtime/` のみを作成します。 `binaries/`、`proxy/`、`rules/` などはパネルまたはコアの取り付け時に作成されます。
> データ ディレクトリは `.env` の `SAFE_PATHS` から取得され、絶対パスである場合があります。インストール ディレクトリを変更しても、既存のデータは移動されません。

### 2.7 サービス管理

systemd (ほとんどのディストリビューション):

```bash
systemctl status corefusion --no-pager
systemctl restart corefusion
systemctl stop corefusion
journalctl -u corefusion -f          # follow logs
journalctl -u corefusion -n 100      # last 100 lines
```

systemdなし（コンテナなど）：

```bash
cd /opt/corefusion && ./corefusion            # foreground (debugging)
cd /opt/corefusion && setsid nohup ./corefusion >> data/logs/panel.log 2>&1 &
tail -f data/logs/panel.log
```

> systemd がないと、起動時にプロセスが開始されません。再起動後に手動で再起動します (またはインストーラーを再実行します)。

### 2.8 アップグレードとアンインストール

アップグレード (データと構成を保持):

```bash
sudo bash install.sh --version <new-version>
```

スクリプトはサービスを停止し、古いバイナリを `corefusion.bak` としてバックアップし、それを置き換えて再起動します。既存の `.env` と `data/` はそのまま残されます。

アンインストール:

```bash
# Remove the program only; keep data and .env
sudo bash install.sh --uninstall

# Also remove the data directory and .env (irreversible)
sudo bash install.sh --uninstall --purge
```

### 2.9 環境ファイル(.env)

完全な `.env` は、構成 (データベース DSN、データ ディレクトリ、シークレット、ポート、ドメイン) が保存されるときに **セットアップ ウィザードによって** 生成されます。

新規インストールでは、インストーラーはこのプレースホルダーのみを書き込むため、パネルが既存の `data/` を初期化されたインストールと誤認してウィザードをスキップすることはありません。

```env
SAFE_PATHS=data
```

> 完全な構成 (`.env` と `CF_DB_DSN`) がすでに存在する場合、インストーラーはそれを上書きせず、ウィザードは再度表示されません。
> 後で `.env` に手動で編集した内容は、再起動後に有効になります。

#### データディレクトリ

```env
SAFE_PATHS=data                       # relative to the install directory
# SAFE_PATHS=/srv/corefusion-data     # or an absolute path
```

#### データベース

`CF_DB_DSN` はプレフィックスによって検出されます。

| プレフィックス | データベース |
|--------|----------|
| 未設定または裸のパス | SQLite (デフォルト) |
| `sqlite://` | SQLite (明示的) |
| `mysql://` | MySQL |
| `postgres://` / `postgresql://` | PostgreSQL |

`CF_DB_TYPE` はオプションであり、検出 (`sqlite` / `mysql` / `postgres`) をオーバーライドします。

> **暗号化されたパスワード**: パネルによって書き込まれた MySQL/PostgreSQL DSN (セットアップ ウィザード/データベース スイッチ)
> は、`.env` に `enc:...` (AES-256-GCM、キー `CF_SECRET_ENCRYPTION_KEY`) として保存されます。
> これらは読み取り時に復号化されます。手動で作成された平文 DSN は引き続き機能します。

**SQLite (デフォルト)**

```env
# Bare path (detected as SQLite)
CF_DB_DSN=data/sqlite/app.db

# Or explicit sqlite:// prefix
CF_DB_DSN=sqlite:///opt/corefusion/data/sqlite/app.db
```

**MySQL**

```env
# Format: mysql://user:password@tcp(host:port)/dbname?params
CF_DB_DSN=mysql://corefusion:password@tcp(127.0.0.1:3306)/corefusion?charset=utf8mb4&parseTime=True&loc=Local
```

**PostgreSQL**

```env
# Format: postgres://user:password@host:port/dbname?params
CF_DB_DSN=postgres://corefusion:password@127.0.0.1:5432/corefusion?sslmode=disable
```

#### 接続プール (オプション、MySQL/PostgreSQL)

```env
CF_DB_MAX_OPEN_CONNS=100
CF_DB_MAX_IDLE_CONNS=10
```

#### その他の一般的な変数

| 変数 | 説明 |
|----------|-------------|
| `JWT_SECRET` | ログイントークンの署名キー。欠落している場合に最初の起動時に生成される |
| `CF_SECRET_ENCRYPTION_KEY` | 機密設定を暗号化するためのキー (AES-256-GCM)。欠落時に生成される |
| `CF_INITIAL_ADMIN_PASSWORD` | 初期管理者パスワード (オプション; デフォルトではランダムで 1 回印刷されます) |
| `CF_NETWORK_TRAFFIC_ACCOUNTING` | iptables ベースのトラフィック アカウンティングを無効にするには、`0` に設定します (デフォルトで有効) |
| `CF_NETWORK_TRAFFIC_TABLE` | トラフィック アカウンティングに使用される iptables テーブル、デフォルトは `corefusion` |

> **暗号化キーは `.env.secret` にあります**: 最初の起動時に、`CF_SECRET_ENCRYPTION_KEY` は `.env` ではなく `.env.secret` (0600、`.env` と同じディレクトリ) に書き込まれます。 `.env` のレガシーキーは自動的に移行されます。このファイルを個別にバックアップします。ファイルを失うと、すべての `enc:` 値が復号化できなくなります。

> 実際のクライアント IP を解決するための信頼されたリバース プロキシは、環境変数を介して構成されなくなりました。
> これらは **[設定] → [ネットワーク]** に `panel.trusted_proxies` として保存されます。

> `.env` と `.env.secret` には両方とも秘密が含まれています。パネルは起動時に権限を `0600` に強化します。決してコミットしないでください。

### 2.10 Docker (オプション、独自のイメージを構築)

リポジトリは Dockerfile を**提供しません**。コンテナ化する場合は、独自のイメージを記述します。参照呼び出し:

```bash
docker run -d \
  --name corefusion \
  -p 8080:8080 \
  -p 18443:18443 \
  -v /opt/corefusion/data:/app/data \
  -v /opt/corefusion/.env:/app/.env \
  <your-image>
```

> 通常、コンテナには systemd 権限も `nft` 権限もないため、レート制限/ファイアウォール機能は機能しません。
> 作業ディレクトリは、相対 `SAFE_PATHS` のベースと一致する必要があります。

### 2.11 インストール後のチェック

```bash
# Environment and dependencies
sudo bash install.sh --cpu-info

# Service state
systemctl is-active corefusion

# Startup log (contains the setup URL and token)
journalctl -u corefusion -n 50 --no-pager

# Listening ports
ss -lntp | grep corefusion
```

## 3. 初期設定

最初の起動時に、`.env` に有効な `CF_DB_DSN` がない場合、パネルはまだ管理 UI を**提供しません**。それは、
**セットアップ ウィザード**は、ワンタイム トークンを使用して 18000 ～ 18999 のランダムなポート上で実行され、保存されると通常のパネルとして再起動されます。

### 3.1 セットアップウィザードを開く

1. インストーラーの出力から「セットアップ ウィザード」URL をコピーします。または
2. サーバー上のログを読み取ります。

```bash
journalctl -u corefusion -n 50 --no-pager | grep -A2 'setup wizard'
```

```text
CoreFusion first start - setup wizard
  URL   : http://<ip>:<port>/init?init_token=<token>
  Token : <token>
  Valid : 2h0m0s
```

3. ブラウザで URL を開きます (すでに `init_token` が含まれているため、手動入力は必要ありません)。

> ウィザード セッションは、デフォルトでは **2 時間**後に期限切れになります。有効期限が切れた場合、またはパネルが再起動した場合は、新しいものを入手してください。
> トークンを共有しないでください。セットアップが完了すると、このポートは閉じられ、通常のパネル ポートのみが残ります。

### 3.2 ウィザードの手順

ウィザードには 8 つのステップがあります。いつでも戻ることができます。最終保存するまで何もコミットされません。

| ステップ | 内容 |
|------|---------|
| 1. データベース | SQLite / MySQL / PostgreSQL |
| 2. データディレクトリ | `.env` で `SAFE_PATHS` に書き込まれます |
| 3. 暗号化キー | `JWT_SECRET` および `CF_SECRET_ENCRYPTION_KEY` |
| 4. コア | どのプロキシ コアをインストールするか |
| 5. プロキシ | なし / Nginx / Caddy |
| 6. サイトとドメイン | ポート、Web パス、管理者アカウント、通貨、タイムゾーン、ドメイン |
| 7.HTTPS証明書 | 無効 / アップロード / ACME |
| 8. まとめ | `.env`を確認してダウンロードし、保存して再起動します |

#### ステップ 1: データベース

- **SQLite (ローカル ファイル、推奨)**: `<data-dir>/sqlite/app.db` を使用するには、パスを空のままにしておきます。
- **MySQL / PostgreSQL**: ホスト、ポート、ユーザー、パスワード、データベース名。 PostgreSQLは`disable` / `require` / `verify-full`もサポートします。
- 「接続をテスト」をクリックして検証します。保存するとテストも行われます。不足しているデータベースは自動的に作成されます (アカウントに `CREATE` がない場合は手動で作成します)。
- DSN (パスワードを含む) は、`.env` に書き込まれる前に暗号化されます。

#### ステップ 2: データ ディレクトリ

データベース、証明書、ログ、コアバイナリなどを保存します。これは`.env`の`SAFE_PATHS`です。デフォルトは`data`
(インストールディレクトリを基準にして);絶対パスが許可されます。 **後から何気なく変更しないでください** またはパネル
既存のデータベースと証明書が見つかりません。

#### ステップ 3: 暗号化キー

- `JWT_SECRET`: ログイン トークンに署名します。
- `CF_SECRET_ENCRYPTION_KEY`: 機密設定 (データベース パスワード、DNS 資格情報、リチャージ カードなど) を暗号化します。
- どちらもデフォルトではランダムに生成されます。新しい値を取得するには「再生成」を使用します。 **`CF_SECRET_ENCRYPTION_KEY` を変更すると、以前に暗号化されたデータが読み取れなくなります** - バックアップしてください。

#### ステップ 4: コア

インストールするプロキシ コアを選択します。

- **Xray**: VLESS / VMess / Trojan / Shadowsocks など;
- **sing-box**: Hysteria2 / TUIC およびその他の QUIC プロトコルを伝送します。

保存して再起動すると、パネルが自動的にダウンロードしてインストールします。 「プロトコル」でバージョンとステータスを確認します。後でインストールすることもできます。

#### ステップ 5: プロキシ

- **なし**: パネルはクライアントに直接サービスを提供します (TLS を自分で処理します)。
- **Nginx / Caddy**: パネルはリバース プロキシと証明書ホスティングを管理します。 1つ選んでください。

プロキシを選択すると、パネルは通常、`127.0.0.1` でのみリッスンし、プロキシは外部にサービスを提供します。

#### ステップ 6: サイトとドメイン

| フィールド | 説明 |
|-------|-------------|
| リッスンアドレス | 自動的に派生: プロキシ → `127.0.0.1`;証明書のあるプロキシなし → `0.0.0.0`;それ以外の場合 → `127.0.0.1` |
| パネルポート | デフォルトではランダムな空きポート。必要に応じて変更してください (例: 8080) |
| サブスクリプションポート | オプション。 `0` はパネル ポートを共有します |
| ポータルポート | オプション。 `0` はパネル ポートを共有します |
| ウェブパス | 管理 UI パス、デフォルトは `/`。 API は常に `/api/v1` です |
| 管理者のユーザー名/パスワード | デフォルトではランダム。 **パスワードは概要に 1 回だけ表示されます** - 保存してください |
| アクセスモード | 「ドメイン」または「IP」 |
| デフォルトの通貨/タイムゾーン | リチャージカードと残高のデフォルト通貨。パネルとプロキシログのタイムゾーン (例: `Asia/Shanghai`) |
| リバースプロキシに追加 | プロキシとドメインを設定したら、パネル/サブスクリプション/ポータルのドメインを一度にプロキシに追加します |

ドメインを入力すると、対応する設定 (コールバック ドメイン、サブスクリプション エンドポイント、共有ドメイン) が書き込まれます。

#### ステップ 7: HTTPS 証明書

| ソース | 説明 |
|--------|-------------|
| HTTPSを無効にする | パネル/ポータル/サブスクリプションは HTTP (安全ではありません) 経由で提供されます。リバース プロキシを使用すると、後でプロキシ側に TLS を追加できます |
| 証明書のアップロード | 証明書 PEM と秘密キー PEM を貼り付けます (ドメイン アクセス モードのみ) |
| ACME | このステップを送信すると証明書が発行されます。ドメイン証明書とIP証明書をサポートします |

ACME オプション:

- **CA**: Let's Encrypt、Let's Encrypt (ステージング)、ZeroSSL、Google パブリック CA。
- **ターゲット**: 構成されたドメインまたはパブリック IP (IP 証明書は Let's Encrypt でのみサポートされます)。
- **チャレンジ**: `HTTP-01` (ポート 80 が必要) または `DNS-01` (ワイルドカード、ポート 80 なし。DNS プロバイダーを選択し、資格情報を入力)。
- **キーのタイプ/サイズ**: ECC 256/384 または RSA 2048/3072/4096。
- **Google パブリック CA**: EAB が必要です。キー ID / HMAC を手動で入力するか、GCP サービス アカウントを使用します。

> IP 証明書は、ホストのパブリック IPv4/IPv6 を自動検出します。プロキシの背後では、検出されたアドレスはホストのアドレスであり、プロキシの出力アドレスではありません。
> ドメイン証明書は、後から「証明書」で発行することもできます。

#### ステップ 8: まとめ

データベース、データ ディレクトリ、コア、プロキシ、ポート、管理者アカウント、ドメイン、`.env` キー (マスクされたシークレット) が表示され、以下が提供されます。

- **.env をダウンロード**: 構成のコピーを保存します。
- **アクセス URL**: パネル/サブスクリプション/ポータルの最終 URL。 HTTP は安全でないとしてマークされています。

「保存して再起動」をクリックしてデータベースと `.env` を書き込みます。パネルは通常のサービスを再開します。

### 3.3 セットアップ後

- サービスが再起動され、起動ログに最終的なリッスン アドレスが出力されます。
- 管理者アカウントでサインインし、概要から URL と Web パスにアクセスします。
- パスワードを紛失した場合は、`./corefusion admin reset-password` を使用してオフラインでパスワードをリセットします。

### 3.4 非対話型 CLI セットアップ

自動化サーバーまたはヘッドレスサーバーの場合は、構成を書き込み、セットアップが完了したことを直接マークします。

```bash
cd /opt/corefusion
./corefusion init \
  --db-type sqlite \
  --data-dir /opt/corefusion/data \
  --admin-username admin \
  --admin-password 'change-me-strong-password' \
  --listen-port 8080 \
  --proxy-type caddy \
  --cores xray,singbox \
  --panel-domain panel.example.com \
  --tls-mode acme --tls-domain panel.example.com --tls-email you@example.com
```

共通フラグ:

| 旗 | 説明 |
|------|-------------|
| `--db-type` / `--db-host` / `--db-port` / `--db-user` / `--db-password` / `--db-name` | データベース設定 |
| `--data-dir` | データディレクトリ。デフォルトは `SAFE_PATHS` または `./data` |
| `--listen-port` / `--subscription-port` / `--portal-port` / `--web-path` | ポートと Web パス (デフォルトではランダムな空きポート) |
| `--admin-username` / `--admin-password` | 管理者アカウント（省略時はランダムなパスワードが1回印刷されます） |
| `--proxy-type` | `none` / `nginx` / `caddy` |
| `--cores` | インストールするコア、カンマ区切り: `xray,singbox` |
| `--panel-domain` / `--subscription-domain` / `--portal-domain` | ドメイン (設定に書き込まれ、リバース プロキシに追加される) |
| `--tls-mode` | `none` / `self_signed` / `acme` |
| `--tls-domain` / `--tls-email` / `--tls-challenge` / `--tls-key-type` / `--tls-key-bits` | 証明書オプション (`--tls-challenge` のデフォルトは `http-01`、`dns-01` には `--tls-dns-channel` または `--tls-dns-provider` が必要です) |
| `--tls-ip-cert` | 検出されたパブリックIPの証明書を発行します(Let's Encryptのみ) |
| `--acme-provider` | `lets_encrypt` / `lets_encrypt_staging` / `zerossl` / `google` |
| `--currency` / `--timezone` | デフォルトの通貨/タイムゾーン |

完全なリスト: `./corefusion init --help`。次にサービスを開始します。

```bash
systemctl restart corefusion
```

### 3.5 セットアップウィザードの再実行

やり直すには (`.env` とセットアップ マークを削除し、**データを保持します**):

```bash
cd /opt/corefusion
./corefusion reset-init      # type RESET to confirm
systemctl restart corefusion
```

次に、新しい URL と起動ログからのトークンを使用します。

> 再初期化すると、管理者アカウントと Web パスがリセットされます。古いデータベース内のビジネス データは残りますが、ログイン アカウントを再作成する必要がある場合があります。
>
> `reset-init` は、`.env` 全体 (`SAFE_PATHS` を含む) を削除します。 **データ ディレクトリがカスタム絶対パスである場合**、再起動する前に `SAFE_PATHS` を復元します。それ以外の場合、パネルは `./data` で表示されます。
>
> ```バッシュ
> printf 'SAFE_PATHS=/srv/corefusion-data\n' > /opt/corefusion/.env
> ```

### 3.6 初回サインイン後のセキュリティ

#### 初期パスワードを変更する

1. 右上隅にあるユーザー名をクリックします。
2. 「パスワードを変更」を選択します。
3. 古いパスワードと新しいパスワードを入力します。
4. 「保存」をクリックします。

#### ダイナミックコードログインを有効にする (2FA / TOTP)

> 有効にすると、アカウントは **動的コード ログイン** に切り替わります。静的パスワードは受け入れられなくなります。だけ
> 認証アプリの 6 桁のコード (またはワンタイム リカバリ コード) が機能します。これはログインパスワードを**置き換えます**。
> 「パスワード + コード」の 2 段階認証ではありません。

1. 右上隅にあるユーザー名をクリックします。
2. 「2FA を有効にする」を選択します。
3. 現在のパスワードを入力します (この変更を確認するためのみ)。
4. 認証アプリ (Google Authenticator / 1Password など) で QR コードをスキャンするか、キーを手動で入力します。
5. 6 桁のコードを入力して有効化を完了します。
6. **リカバリ コードをすぐに保存します** (ダウンロード可能)。各コードは一度だけ機能します。

その後サインインします:

- ユーザー名を入力すると、パスワードフィールドが「6桁のコード/リカバリコード」に変わり、ボタンが「コードでサインイン」に変わります。
- 現在のコードを入力します。 **静的パスワードは使用できなくなりました**。
- リカバリ コードは 1 回限りの使用です。不足した場合は、「動的コード ログイン (2FA)」で再生成します (これにより、古いコードはすべて無効になります)。

オーセンティケータが失われ、リカバリ コードが使い果たされた場合は、サーバー上で 2FA オフラインを無効にします。

```bash
cd /opt/corefusion
./corefusion admin 2fa reset -u admin    # disables 2FA, clears the secret and recovery codes, revokes all sessions
```

> 認証コードも回復コードも持たない唯一のスーパー管理者は、Web UI から回復できないため、上記のコマンドを使用する必要があります。

#### Passkey を登録する (オプション)

1. 右上隅にあるユーザー名をクリックします。
2. 「Passkey管理」を選択します。
3. 「新しいPasskeyを登録」をクリックします。
4. デバイスのプロンプトを完了します。

> **注意**: パスキーには HTTPS または localhost が必要で、ドメインは許可リストに登録されている必要があります。

## 4. ダッシュボード

ダッシュボードには、マルチノード クラスターの概要とノードの健全性が表示されます。

### 4.1 表示内容

- **システム情報**: ホスト名、OS バージョン、稼働時間、CPU、メモリ
- **トラフィック**: リアルタイム帯域幅、総トラフィック、月次傾向
- **ノードの健全性**: オンライン/オフライン/劣化した数、高負荷ノード
- **アラート**: オフライン ノード、機能低下したノード、まもなく期限切れになる証明書、クォータ警告
- **クラスター リソース**: 平均 CPU、メモリ、ディスク、およびスループット

### 4.2 アクション

- 「詳細を表示」をクリックしてノードの詳細ページを開きます
- ノード カードをクリックすると、そのライブ ステータスが表示されます
- フィルターを使用してステータス、タイプ、または地域で絞り込みます

## 5. ノード管理

ノード管理は CoreFusion の中核であり、複数のノード タイプをサポートします。

### 5.1 ノードの種類

| 種類 | 説明 |
|------|-------------|
| スタンドアロン (`standalone`) | 独立したコアノード |
| ミラー(`mirror`) | ターゲットノードから構成を同期します |
| プライマリ/バックアップ (`primary_backup`) | 相互にフェイルオーバーするパートナー ノード |
| チェーンエントリー (`chain_entry`) | チェーンされたプロキシのエントリ ノード |
| チェーン出口 (`chain_exit`) | チェーンされたプロキシの出口ノード |

### 5.2 ノードの追加

1. 「ノード管理」を開きます。
2. 「サーバーを追加」をクリックします。
3. 基本事項を入力します。
   - 名前、例: `HongKong-HK01`
   - ホスト名: IP またはドメイン
   - 地域、例: `HK`、`JP`、`US`
   - ノードタイプ。
4. エージェントのポートを設定します (デフォルトは `18443`)。
5. サポートされているコアを選択します。
6. 「保存」をクリックします。

### 5.3 ワンクリック展開

1. ノードを追加した後、ノードリストで「Deploy command」を選択します（詳細ページには、
 「ブートストラップ インストール コマンド」);
2. コマンドをコピーします。これには 1 回限りの登録トークン (24 時間有効、再利用不可) が含まれています。
3. リモート ノード上で root として実行します。それは次のようになります:

   ```bash
   bash <(curl -fsSL "http://<panel-host>:<panel-port>/api/v1/agent/install?id=<node-id>&token=<one-time-token>&port=<panel-port>")
   ```

4. エージェントはパッケージをダウンロードし、パネルに登録して開始します。

### 5.4 ノードの詳細

ノードをクリックして詳細ページを開きます。

- **概要**: 基本情報、エージェントのステータス、証明書のステータス。リソース カードには、CPU / メモリ / ディスク使用量、NIC アップ/ダウン レート、コア ユーザー トラフィック レート、月間使用トラフィック、TCP 接続、システム負荷および出力 NIC 累積トラフィックが表示されます (10 秒ごとのサイレント更新)。
- **プロトコル センター**: コア プロセス構成
- **プロキシ**: Caddy / Nginx 構成
- **コアプロセス**: 開始 / 停止 / 再起動
- **コア トラフィック**: コアによって転送されるユーザー トラフィックとその月次合計
- **WARP**: WARP 設定
- **直接ドメイン**: ドメイン管理
- **レート制限**: トラフィック シェーピング
- **証明書**: 証明書バインディング
- **オンライン ユーザー**: リアルタイム オンライン ユーザー

### 5.5 ノードのアクション

- **構成を同期**: パネル構成をノードにプッシュします
- **強制再接続**: エージェント接続を切断し、再接続します。
- **エージェントの更新**: エージェントの更新をプッシュします
- **証明書の取り消し**: ノードのエージェント証明書を取り消します。

## 6. プロトコルセンター

プロトコル センターは、コア プロセスのプロトコル パラメーターを構成します。

### 6.1 サポートされるコア

| コア | 説明 |
|------|-------------|
| Xrayコア | VLESS / VMess / Trojan / Shadowsocks など |
| sing-box | TUN をサポートするモジュール式ユニバーサル プロキシ プラットフォーム。 Hysteria2 / TUIC およびその他の QUIC プロトコルを搭載 |

### 6.2 構成モジュール

モジュールは 2 つのコア間で異なります。パネルには、選択したコアに一致するセットが表示されます。

**Xray-コア**

- **ログ**: アクセスログ、エラーログ、出力モード
- **API**: gRPC API リッスン アドレス、サービス リスト
- **DNS**: DNS サーバー、クエリ戦略、静的ホスト
- **ルーティング**: ルーティング ルール、ロード バランシング、VLESS ルーティング
- **インバウンド/アウトバウンド**: プロトコル、トランスポート、TLS
- **トランスポート**: WebSocket、gRPC、XHTTP など (TUN は受信プロトコルであり、トランスポートではありません)
- **TLS**: 証明書、ALPN、uTLS フィンガープリント、ECH
- **Reality**: ターゲット管理、キーペア、短縮 ID
- **ヘルスチェック / FakeDNS / メトリクス / ポリシー / 地域データ / バージョン制限**: プローブ、IP プール、Prometheus、タイムアウトとバッファ、リソース ファイル、コア バージョン範囲

**sing-box**

- **ログ**: レベル、タイムスタンプ、出力
- **NTP**: 時刻同期
- **DNS**: DNS サーバーとルール
- **ルーティング**: `final` デフォルトのアウトバウンド、**ルール セット**、**ルール**、デフォルトのドメイン リゾルバー、ネットワーク戦略およびフォールバック (6.6 を参照)
- **インバウンド/アウトバウンド**: プロトコル、トランスポート、TLS
- **エンドポイント**: WireGuard (WARP 構成を含む)、MASQUE クライアントなど。いくつかは共存でき、`tag` によって区別されます。

> 「システム ネットワーク統合の使用」を有効にすると、エンドポイントの **名前** はカーネル インターフェイス名になります。
> 最大 15 文字、文字/数字/`._-` のみ。長すぎる名前または無効な名前は自動的にフォールバックします
> エンドポイント `tag` に送信します。新しいエンドポイントにはプロトコルごとにプレフィックスが付けられます (`wg-` / `ts-` / `oc-` / `ovpn-c-` /
> `ovpn-s-` / `mq-c-` / `mq-s-`)、および `WireGuard-xxxxxx` などのレガシー レコードは正規化されて表示されます。
> エディタを開いた瞬間に。
- **サービス**: 最上位の sing-box `services` アレイ (`hysteria-realm`、DERP、`resolved` など)
- **証明書 / HTTP クライアント / ネットワーク名前空間**: 必要な場合にのみ展開する JSON セクション
- **実験中**: `clash_api` および類似品。 **有効にしない限り、生成された構成には何も書き込まれません**

> sing-box 1.12 では、`geosite` / `geoip` ルーティング フィールドが削除されました。地理ベースのルーティングが通過するようになりました
> `rule_set`。古いフィールドを保持すると、コアは設定のデコードに失敗します (`unknown field`)。

### 6.3 インバウンド構成

1. コアとプロトコルを選択します。
2. 基本事項を入力します。
   - タグ
   - リッスンアドレスとポート
   - プロトコルの種類
3. プロトコルパラメータ（UUID、パスワードなど）を設定します。
4. トランスポート (TCP、WebSocket、gRPC など) を選択します。
5. TLS (証明書、ALPN) を構成します。
6. 保存してコアに適用します。

> 新しい受信はデフォルトで `::` でリッスンします (Linux のデュアル スタック、IPv4 と IPv6 の両方を処理します)。
> インターフェースを制限する必要がある場合にのみ、`0.0.0.0` または特定のアドレスに変更してください。

「受信ポートを使用する」ポート モードでは、**ファイアウォール許可ルールを自動的に作成**することもできます。
インバウンドエディターは最初にノードのファイアウォールを調査し、firewalld / ufw / nftables / iptables が検出されると
リスニング プロトコル (TCP/UDP) に従って保存時にポートを許可できます。

- hy2 / hysteria ポート ホッピングでは、リスニング ポートとすべての動的ポート範囲 (例: `20000-30000`) の両方が許可されます。複数の範囲はカンマで区切られます。
- 許可は冪等です。既存の対象ルール (ポート範囲/マルチポート) は再度作成されません。
- ポートを変更すると、新しいルールが許可される前に古いルールが取り消されます。インバウンドを削除し、ポートホッピングを無効にするか、Unix Socket / tun (リスニングポートなし) に切り替えるとクリーンアップされます。
- 有効なファイアウォールが検出されない場合は、ヒントのみが表示され、ルールは書き込まれません。

**輸送と流れ**:

- `xtls-rprx-vision` は生の TCP 上でのみ機能します。gRPC / XHTTP / WebSocket では、クライアントは完全に失敗するか (sing-box: `initialize vision: not a valid supported TLS connection`)、サーバー フロー チェックに同意しません (`flow mismatch`)。パネルは、保存時および実行時設定の生成時に、非 raw/TCP 受信からビジョンを取り除きます。
- sing-box トランスポートは http / ws / quic / grpc / httpupgrade のみです — **生の TCP はトランスポートがまったくないことを意味します**。トランスポート ドロップダウンの最初の (空の) エントリは生の TCP です。 `type: "tcp"` を書き込むと、コアが設定を拒否します。

### 6.3.1 リバースプロキシパス（アクセスドメイン→フロントTLS→リバースプロキシパス）

インバウンド自身のトランスポート パスが `/` であるが、外側の nginx / caddy がそれをサブパスの下にマウントする場合
(例: `location /apps { proxy_pass http://127.0.0.1:8080/; }`)、クライアントは `/apps` または
リクエストはその場所に到達しません。サブスクリプションは引き続きダウンロードされますが、ノードは接続されません。
「アクセス ドメイン → フロント TLS」の下に **リバース プロキシ パス**を入力します。

- `/apps` または `/apps?ed=2560` (初期データあり) を入力します。サブスクリプションと共有リンクは、受信トランスポート パスを**置き換え**します。
- ws、httpupgrade、xhttp、および h2/http に適用されます。パスのないトランスポート (raw/tcp、kcp) は無視されます。
- これは、TLS がどこで終了するかには関係ありません。パスは、フロント TLS がオフの場合でも適用されます (コアに従う)。
- gRPC には URL プレフィックスの概念がない (クライアント パスは常に `/{serviceName}/…`) ため、パスは **serviceName にマージされます**
(`/apps` + `svc` → `apps/svc`);リバース プロキシは、`grpc_pass` のプレフィックスを削除する必要があります。

### 6.3.2 SNI ベースのルーティング (nginx と Caddy)

前置 TLS は `:443` 上で ClientHello の SNI ごとに接続を振り分けます。プロトコルセンターの REALITY 入站は
ルールを自動生成し、「プロキシ管理 → SNI」で手動追加もできます。どちらのプロキシもドメイン単位で振り分けられますが、
PROXY protocol の適用範囲が異なります。

| | nginx (stream) | Caddy (layer4) |
|---|---|---|
| `proxy_protocol` の範囲 | パネル同梱の nginx（`stream_pp_var` パッチ入り）：**SNI ルールごと**に v1 / v2 / オフ。公式または未パッチの nginx：listen グループ全体（`listen` レベル）で、ポート単位に全開か全閉 | ルートごと（`proxy ... { proxy_protocol v2 }`） |
| 同じ `:443` で xray + sing-box | パッチ適用後は対応：xray の REALITY は v1/v2、sing-box のルールはオフ | 対応：一方の SNI を xray（PP v2）、他方を sing-box（PP なし）へ |
| sing-box への到達方法 | パッチ後は xray と `:443` を共有可能（該当ドメインは PP オフ）。それ以外は専用ポート、または PP なしの別 listen グループ | xray と `:443` を共有し、SNI で分離 |

補足：

- 既定値は従来どおり `v1`（旧 `proxy_protocol on`）。SNI サイトごとに `v1` / `v2` / オフを選択できます。`v2` はバイナリ
  ヘッダー（IPv4 で 28 バイト）で、v1 のテキストヘッダー（約 50〜60 バイト）より短くなります。差は接続時1回だけで、
  実用上は体感できません。
- パネルは Agent 経由で `nginx -V` を実行し、`NGX_STREAM_PP_VAR`（能力フラグ `stream_pp_var`）を検出します。結果は
  60 秒キャッシュされます。未パッチ、検出失敗、旧 Agent の場合はグループ全体の `proxy_protocol on`（v1）に戻し、
  sing-box の自動 SNI 派生ルールをスキップします（ログ `skipped N sing-box REALITY SNI rule(s)`）。`nginx -t` に
  失敗する設定は生成しません。
- sing-box の REALITY / anytls は PROXY ヘッダーを受け取れないため、派生ルールは常にオフです。手動で v1/v2 にすると
  ハンドシェイクが壊れます。
- リバースプロキシ配下の xray は、実クライアント IP とポートを得るために PROXY protocol が必要です
  （`sockopt.acceptProxyProtocol`）。`realitySettings.xver` は xray が dest へ送るもので、こことは無関係です。
- 「Reality テンプレート」の `singbox_listen_port` は**ローカル TLS エンドポイント**（xray の dest / sing-box の
  handshake）で、両プロキシが対応し、上記の公開 SNI 振り分けとは別物です。

### 6.6 sing-box ルーティングとルール セット

「プロトコル センター」 → sing-box → 「ルーティング」には 2 つの部分があります: **ルール セット** は再利用可能を宣言します。
ルール ファイルと **ルール** により、一致条件と送信が決定されます。ルールは次から評価されます
上から下へ、最初の試合が勝ちます。

#### 6.6.1 ルールセット

| フィールド | 説明 |
|-------|-------------|
| タグ | ルールによって参照されるルールセット識別子。一意である必要があります |
| 種類 | `local` はノード上のファイルを読み取ります。 `remote` により、コアが `update_interval` にダウンロードできるようになります |
| フォーマット | `.srs` の場合は `binary` (デフォルト)。ソース形式 `.json` の場合は `source` |
| パス | `local` パスはノード データ ディレクトリに対する相対パスです。 `data/rules/` のファイルは `rules/xxx.srs` を使用します |
| URL | `remote` のダウンロード アドレス; `download_detour` は、ダウンロードに使用されるアウトバウンドを選択します (通常は `direct`) |

ローカル ルール セット (推奨。最初に「サービス リソース → ルール ファイル」でファイルをダウンロードします):

```jsonc
"route": {
  "rule_set": [
    { "type": "local", "tag": "geosite-cn", "format": "binary", "path": "rules/geosite-cn.srs" },
    { "type": "local", "tag": "geoip-cn", "format": "binary", "path": "rules/geoip-cn.srs" }
  ]
}
```

> パネルにファイルをダウンロードするだけでは十分ではありません。まず、`local` ルール セットをパネルにプッシュする必要があります。
> ノード (「すべてのノードにプッシュ」) により、ファイルはノードの `data/rules/` に存在します。それ以外の場合はコア
> ファイルが見つからないため起動に失敗します。

リモート ルール セット (ノードは URL に到達できる必要があります):

```jsonc
{ "type": "remote", "tag": "geosite-openai", "format": "binary",
  "url": "https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-openai.srs",
  "download_detour": "direct", "update_interval": "1d" }
```

ローカル ファイルを選択すると、タグはファイル名から派生します (`rules/geosite-cn.srs` →
`geosite-cn`);リモート セットの場合は、URL の端から来ます。フォーマットも次から入力されます。
内線番号（`.srs`→`binary`、`.json`→`source`）。派生した値は自由に編集でき、
すでに入力した値が上書きされることはありません。

> `download_detour` は sing-box 1.14 以降非推奨となり、1.16 で削除される予定です。それはまだ
> 1.15で動作します。新しい構成では、トップレベルの `http_clients` を使用する必要があります。
> 代わりに`route.default_http_client`。

#### 6.6.2 ルール

| フィールド | 一致 |
|-------|---------|
| `domain` | 正確なドメイン |
| `domain_suffix` | ドメインサフィックス（サブドメインを含む） |
| `domain_keyword` | 部分文字列一致 |
| `domain_regex` | 正規表現 |
| `ip_cidr` / `ip_is_private` | 宛先IP |
| `source_ip_cidr` | 送信元IP |
| `port` / `port_range` | 宛先ポート |
| `network` | `tcp` / `udp` |
| `rule_set` | 使用するルールセットのタグ |
| `outbound` | 使用する送信タグ (「送信」または「エンドポイント」の下に存在する必要があります) |
| `type: "logical"` | `mode`を`and` / `or`に設定した組み合わせ条件 |

1 つのルール内の複数のフィールドは AND で結合されます (たとえば、`network` + `port`)。
`logical` ラッパーが必要です。 `type: "logical"` は OR / NOT の組み合わせにのみ使用します。 `rule_set`
は、`rules` の隣ではなく、`rules` サブルール内に配置する必要があります。

```jsonc
"rules": [
  { "domain_suffix": ["gstatic.com", "googleapis.com"], "outbound": "direct" },
  { "domain_keyword": ["ip.sb", "yandex.com"], "outbound": "warp" },
  { "rule_set": ["geosite-openai", "geosite-google"], "outbound": "warp" },
  { "rule_set": ["geoip-cn"], "outbound": "warp" },
  { "network": "tcp", "port": 443,
    "rule_set": ["geosite-google"], "outbound": "warp" },
  { "type": "logical", "mode": "or",
    "rules": [
      { "rule_set": ["geosite-google"] },
      { "rule_set": ["geosite-openai"] }
    ],
    "outbound": "warp" }
]
```

#### 6.6.3 xray ルールの移行

| xray | sing-box |
|------|----------|
| ベア文字列 (`domain` のベア値を含む、部分文字列一致) | `"domain_keyword": ["ip.sb"]` |
| `"domain": ["a.com"]` | `"domain_keyword": ["a.com"]`;実際のサフィックス一致には `"domain_suffix": ["a.com"]` を使用し、完全一致には `"domain": ["a.com"]` を使用します。 |
| `"domain:clstorage.net"` | `"domain_suffix": ["clstorage.net"]` |
| `"full:a.com"` | `"domain": ["a.com"]` |
| `"regexp:..."` | `"domain_regex": ["..."]` |
| `"ip": ["geoip:cn"]` | `"rule_set": ["geoip-cn"]` |
| `"domain": ["geosite:cn"]` | `"rule_set": ["geosite-cn"]` |
| `"outboundTag": "direct"` | `"outbound": "direct"` |

注:

- **タグはコア間で共有されません**: xray 送信タグは sing-box ルールでは使用できません。
 sing-box「アウトバウンド」または「エンドポイント」の下に実際に存在するタグを使用してください。
- 間違ったアウトバウンドタグまたはエンドポイントタグは `outbound not found` を報告します。間違ったルールセットタグが報告する
 `rule-set not found`。
- 直接/許可リスト ルールを最初に置きます。ルールが一致すると、それ以降のルールは適用されなくなります。

## 7. プロキシ管理

プロキシ管理は、Caddy または Nginx リバース プロキシを構成します。

### 7.1 プロキシの種類

- **Caddy**: 自動 HTTPS、HTTP/1.1 および HTTP/2 (HTTP/3 / QUIC は、レイヤー 4 ルーティングとの UDP 443 の競合を回避するために無効になっています)
- **Nginx**: 高性能、柔軟な構成

### 7.2 サイト構成

1. 「プロキシ管理」を開きます。
2. プロキシ タイプ (Caddy / Nginx) を選択します。
3. サイトを追加します。
   - ドメイン
   - 上流
   - ローカルポート
4. 保存します。

### 7.3 フィールド

- **アップストリーム**: バックエンドアドレス、例: `127.0.0.1:8082`
- **local_port**: ローカルリッスンポート、例: `8443`
- **portal_forward**: ポータル転送ルール
- **subscription_forward**: サブスクリプション転送ルール
- **SNI ルーティング**: インバウンドが TLS / REALITY を使用し、クライアントが常に 443 で接続する場合、パネルは次のようになります。
 443 ClientHello SNI からの TCP ルーティング ルール (xray `streamSettings` と sing-box `tls.reality` の両方)。
 フロント プロキシは TCP のみを転送し、TLS は依然としてコア内で終端されます。

## 8. リソースのルーティング

ルーティング リソースは、サブスクリプションとルーティングで使用される共有アセットを収集します。このページには 5 つのタブがあります。

| タブ | 目的 |
|-----|---------|
| Direct および CF 優先ドメイン | 受信直接ドメイン/IP および Cloudflare 優先ドメイン。サブスクリプションおよび外部ノードのアクセス アドレスを書き換えるときに使用されます。 |
| CF IP プール | 「アクセス ドメイン」によって使用される、優先 IP ソース、ポート、およびプローブ設定 |
| WAF グローバル ルール | リバースプロキシ WAF のルール ソースとルール ファイル（ノードにプッシュ） |
| ルールファイル | ルール ファイルのダウンロード、スケジュールされた同期、およびプッシュ (`.srs` / `.json` / `.dat`) |
| 外部ノード | v2ray URI / Base64 / サブスクリプション URL から外部ノードをインポートします (16.3 を参照) |

### 8.1 Direct および CF の優先ドメイン

- **直接アクセス**: イングレス ドメインまたは IP、デフォルトではポート 443。ノードをバインドするか、グローバルの場合は空のままにします。
- **CF 優先ドメイン**: Cloudflare 優先ドメインとポート、接続チェックあり。
- どちらも、サブスクリプションと外部ノードの書き換えで使用される「アクセス ドメイン」候補をフィードします (16.3 を参照)。

- **エントリ ドリフト (プライマリ/スタンバイ)**: 直接エントリは DNS チャネルとレコード名をバインドできます。フェイルオーバーまたはスイッチバックの後、パネルは現在のプライマリのパブリック IP (空の場合は内部 IP) で A レコードをポイントします。 DNS ライターが実装されているプロバイダーのみが受け入れられます (`cloudflare` 検証済み、alidns / DNSPod / GoDaddy / Namecheap / Route53 / Google / Huawei Cloud 実装されているが検証されていない)。 Cloudflare の伝播は、TTL を 60 に固定して約 2 ～ 2.5 分で測定されました。 TCP/REALITY エントリーではオレンジ色の雲をオフにしてください。

### 8.2 CF IP プール

- 優先 IP ソース (`bestproxy` スタイルのソースを含む)、フェッチ間隔、およびポートを維持します。
- 「プローブ設定」は、プローブ間隔、レイテンシしきい値、プローブ エントリ ノードを制御します。ローカルプロービング
 明らかに到達不可能な IP のみをフィルタリングし、エントリ ノードを選択するとそのノードの回線がシミュレートされます。
- 「ダイヤラ」は自動 (コアがインストールされている)、`singbox`、`xray`、または `mihomo` の場合があります。そうでないコア
 インストールされているものはリストされていません。プローブは一時プロセスとして実行され、完了すると終了し、読み取りや読み取りは行われません。
 コア自体の構成を書き込みます。
- 「アクセス ドメイン」が具体的な値を指定せずに CF IP プールを使用する場合、1 つのエントリ (そのポートを含む) が
 ランダムに選ばれました。

### 8.3 WAF グローバル ルール

- WAF ルール ソース URL と同期するルール ファイルを構成します。
- 同期後、それらはノードにプッシュされ、ノード プロキシ (Nginx / Caddy) によってロードされます。
- 完全な URL を持つファイルは、その URL からダウンロードされます。それ以外の場合は、「ソース URL + /ファイル名」が使用されます。
- 「マッチ キャッシュ」 (`match_cache` / `config_match_cache`) はデフォルトで有効になっており、プロセス全体の境界が設定されています。
 ホット ルール マッチ結果のキャッシュにより、リクエストごとのルール トラバーサルが削減されます。グローバルのみであり、
 ドメインごとの上書き。誤検知を調査する際の A/B 比較のために一時的に無効にします
 (無効にすると、すべてのリクエストで完全なルールが評価され、CPU 使用率が高くなります)。

### 8.4 ルールファイル（ルーティングルールファイル）

このタブは、ルール ファイルをパネルにダウンロードし、ノードにプッシュするだけです。何も効力を持たない
自動的に。ルーティングで使用するには、「プロトコル センター → sing-box → ルーティング」で参照します。
ルールセットとルール (6.6 を参照)。

- **ルール リポジトリ**: `owner/repo` (GitHub、参照可能) または完全ダウンロード URL を入力します。予定されている
 同期は 6 ～ 12 時間ごと、毎日 03:00、毎日深夜、または毎週日曜日に実行できます。
- **ファイルの追加**: リポジトリ リリース外の単一ファイルの場合 (SagerNet `.srs` ブランチなど)
 ファイル);完全な URL を入力すると、自動的にダウンロードされます。
- **ファイルリスト**: 名前、サイズ、最終更新、およびファイルごとの「ダウンロード」を含む「自動同期」スイッチが表示されます。
 上部の「すべてのノードにプッシュ」ボタンを押すと、すべてのルール ファイルがすべてのノードにプッシュされます。
- ファイルはパネルの `data/rules/` にダウンロードされ、プッシュされるとノード データの下に保存されます。
 ディレクトリの `rules/`; sing-box では `rules/<file name>` として参照します。
- フォーマット:
  - `.srs`: sing-box バイナリ ルール セット、推奨かつ最小。
  - `.json`: ソース形式ルール セット。 `rule_set` は `format: "source"` を設定する必要があります。
  - `.dat`: xray `geosite.dat` / `geoip.dat`。sing-box は直接使用できません。

> ページ上部の折りたたみ可能な「使用法」ブロックには、参照例、xray マッピングが含まれています。
> 表と一般的なエラー。

## 9. サブスクリプションセンター

サブスクリプション センターは、ノードをクライアント対応のサブスクリプションにパッケージ化します。サブスクリプション **形式** (何を発行するか、どのルール、どのプランがそれらを参照できるか)、次にサブスクリプション **エンドポイント** (パブリック ドメイン / パス) を定義してから、リンクを配布します。

### 9.1 サブスクリプション形式

「サブスクリプションセンター」→「サブスクリプション形式」;クライアント出力ごとに 1 行:

| フィールド | 説明 |
|---|---|
| 名前 | ユニークです。 `?config=<name>` が一致し、顧客ダイアログにそれが表示されます |
| クライアントの種類 | clash / shadowrocket / singbox / v2ray — グループ化のみを表示 |
| 出力フォーマット | `mihomo_yaml` (Clash/Mihomo)、`singbox_json`、`xray_json`、`base64_uri`、`raw_uri` |
| Content-Type / 拡張子 | 応答ヘッダーとファイル名 |
| プラットフォーム | 勝利/マック/android/ios/ユニバーサル; `?platform=` と一致、空 = ユニバーサル |
| 限定された計画 | 空 = すべてのプランで利用可能。それ以外の場合は、それらのプランのみがそれを使用できます |
| ルール | フォーマットごとのルーティング ルール (Mihomo の場合は構造化エディター、sing-box / Xray の場合はルールごとの生の JSON)。 **ルールは形式間で変換されません** |

注:

- 同じ出力形式に対して複数の構成が存在する場合があります (例: `out`、`home`)。リンクに `config=` が含まれているものを選択してください。
- `config` がない場合、順序は「サブスクリプションにバインドされた構成 → `platform` の一致 → デフォルト」になります。
- sing-box テンプレートは、クライアント用に独自の `route.rule_set` (通常は `remote` として) を保持する場合があります。
 クライアントがそれをダウンロードします。 「ルール ファイル」でノードの `rules/` にプッシュされたローカル ファイルのみが利用可能です
 クライアントのサブスクリプションではなく、そのノードのコアに送信されます。
- sing-box / Xray テンプレートを生成するとき、パネルは未解決の参照 (`final`、`dns.final`、
 `default_domain_resolver`、`download_detour`、ローカル `rule_set`、無効な `rule_set` 定義、空
 `balancer` など) なので、クライアントは起動時に致命的なエラーで失敗しません。
- ルール内の送信エイリアスは実際のタグに対して解決されます (`REJECT` / `blocked` → `block`、`DIRECT` →
 `direct`、大文字と小文字は区別されません)。解決できないアウトバウンドはデフォルトのアウトバウンドとルールにフォールバックします。
 その位置を維持します。
- `tag = proxy` を持つグループが常に生成されます。`selector` には sing-box、`random` バランサーは
 ルール内の Xray および `outbound: proxy` は、一致する `balancerTag` に書き換えられます。ルールエディターがロードされます
 送信候補は「プロキシ グループ + カスタム送信」から動的に抽出され、手動で入力されたタグは
 まだ検証済みです。
- sing-box / Xray 構成は個別に作成する必要があります。存在しない場合、顧客リンクには表示されません (10.3 を参照)。

- Mihomo の構造化ルール エディターは論理ルールをサポートします。 `AND` / `OR` / `NOT` / `SUB-RULE`: 条件を `((NETWORK,UDP),(DST-PORT,3478/19302))` として書き込みます。 `SUB-RULE` の場合、3 列目はサブルール グループ名です。条件は括弧で囲む必要があります。
- ルール タイプは最新の mihomo に準拠しています: `IP-SUFFIX`、`SRC-IP-CIDR/SRC-IP-SUFFIX/SRC-IP-ASN/SRC-GEOIP`、`IN-PORT/IN-TYPE/IN-USER/IN-NAME/REMATCH-NAME`、`PROCESS-NAME-WILDCARD/REGEX`、`PROCESS-PATH-WILDCARD/REGEX`、`UID`、`DSCP` はすべて利用可能です。
- `SUB-RULE` は、mihomo 設定の `sub-rules:` ブロックを参照します。パネルはそのブロックをまだ編集していないため、最初に YAML インポートまたは共有 config_json を通じて定義します。

### 9.2 サブスクリプションエンドポイント

「サブスクリプション センター」→「サブスクリプション エンドポイント」;パブリック アドレスごとに 1 行:

| フィールド | 説明 |
|---|---|
| ドメイン | パブリックサブスクリプションドメイン |
| パス | ドメインの下のプレフィックス、デフォルトは `/` |
| 有効 | 無効化されたエンドポイントはリンクの構築時に無視されます |
| 説明 | 自由記述メモ |

- **複数の行 (マルチドメイン)** がサポートされています。いくつかが有効になっている場合、プロバイダー ドメインは現在のリクエストで使用されているドメインに従います (9.4 を参照)。
- 専用のサブスクリプション ポートがルート (`/<token>`、`/sub` なし) で機能します。パネルポートを共有する場合は `/sub/<token>` です。
- リバース プロキシは `X-Forwarded-Proto` / `X-Forwarded-Host` を転送する必要があります。転送しない場合は、最初に有効になったエンドポイントが使用されます。パネルで生成された Caddy / Nginx サイト テンプレートには、両方のヘッダーが含まれています。手動で管理されているプロキシ構成では、手動で追加する必要があります。

### 9.3 サブスクリプションリンク

基本形状：`https://<sub-domain>/<token>`（パネルポート：`https://<panel-domain>/sub/<token>`）

| パラメータ | 説明 |
|---|---|
| `format` | 出力形式。エイリアス: `clash` → mihomo_yaml、`singbox`/`sing-box` → singbox_json、`xray` → xray_json、`raw` → raw_uri、`base64`/`v2ray` → Base64_uri |
| `config` | サブスクリプション形式を名前で適用します。 `format` と一致する必要があります。一致しない場合は無視されます |
| `platform` | プラットフォームごとに設定を一致させる (`config` を省略した場合) |
| `providers` | `1` / `true`: Clash プロバイダー モード (`proxy-providers` + `use`);デフォルトのインラインノード |

例:

```bash
# Clash dynamic subscription (config template + providers)
https://sub.example.com/<token>?format=clash&config=out&providers=1

# sing-box / Xray (only meaningful when such a config exists)
https://sub.example.com/<token>?format=singbox_json&config=sing-box-home
https://sub.example.com/<token>?format=xray_json&config=xray-home

# generic clients / plain text
https://sub.example.com/<token>?format=base64_uri
https://sub.example.com/<token>?format=raw_uri
```

### 9.4 マルチドメインとプロバイダーモード

`providers=1` では、すべての `proxy-providers` エントリがサブスクリプション エンドポイントを指します。ドメインの選択:

1. **このリクエストが使用したドメイン** (**有効な** エンドポイントと一致する場合は、`X-Forwarded-Host` 最初の値、ポートが除去され、それ以外の場合は `Host`)。
2. それ以外の場合は、**最小の ID** を持つ有効なエンドポイント。
3. パスはそのエンドポイントからのものです: `https://<domain><path>/<token>?format=mihomo_proxies_yaml...`。

そのため、ドメインを変更する場合にパネルを変更する必要はありません。新しいドメインを介して取得するクライアントはプロバイダー内で新しいドメインを取得し、有効のまま残された古いドメインはハードコーディングされなくなります。クライアントが古いプロバイダー URL をキャッシュした場合は、サブスクリプションを更新します (またはプロバイダーのキャッシュをクリアするか、クライアントを再起動します)。

追加メモ:

- 共有フォーマット (`config_json`) 内の `proxy-providers` は無視されます (プラン間の漏洩を回避します)。プロバイダーはプラン ノード グループおよび外部ソースから取得されます。
- 内部および外部プロバイダーのキャッシュ パスは、常に「内部プロバイダーのデフォルト → キャッシュ パス テンプレート」(デフォルトは `./providers/{key}.yaml`) から導出されます。外部ソースは独自の設定を行うことはできません。
- 従来の予約済みプロバイダー `subscription-nodes` は発行されなくなりました。「すべてのノード」を使用するグループは、具体的なプロバイダー、またはプランに何もない場合はインライン ノードに拡張されます。

## 10. 顧客管理

顧客管理はエンドユーザーを扱います。

### 10.1 顧客の追加

1. 「顧客管理」を開きます。
2. 「顧客を追加」をクリックします。
3. 記入してください:
   - 電子メール
   - パスワード
   - 計画
   - トラフィック割り当て
   - 有効期限
4. 保存。

### 10.2 顧客の行動

- **編集**: 顧客の詳細を変更します
- **一時停止**: サービスを一時停止します
- **再開**: 停止された顧客を復元します
- **トラフィックをリセット**: 使用されたトラフィックをリセットします
- **パスワードのリセット**: 顧客のパスワードをリセットします
- **更新**: 有効期限を延長します
- **アップグレード/ダウングレード**: プランを変更します。
- **削除**: 顧客を削除します

### 10.3 サブスクリプションの詳細

顧客管理→「購読」欄→「詳細」。ダイアログには、顧客のプランで利用可能なすべての形式のリンクがリストされます。

- **Clash / Mihomo**: 2 行 - インライン ノードと `providers=1` (プロキシ プロバイダー)。両方とも `config=<name>` を保持します。
- **Sing-box / Xray**: その形式の構成が存在し、プランに表示される場合にのみ表示されます。リンクには `config=<name>` が搭載されています。
- **Base64 URI / Raw URI**: 常に表示されます (`config` はありません)。
- 各行には独自のコピー ボタンがあります。行をクリックすると、下の QR コードがその形式に切り替わります。

したがって、Clash 構成のみの場合、ダイアログには Clash + Base64 + Raw が表示されます。 sing-box / Xray リンクは、構成が作成された後にのみ表示されます。

同じダイアログには、トラフィック使用量、注文履歴、取引履歴も表示されます。

## 12. リチャージ管理

リチャージ管理は、リチャージ サイト、注文、およびリチャージ カードを処理します。

> **支払いの統合**
>
> このパネルは **決済機関** (Alipay、WeChat Pay、Stripe、銀行など) と直接統合されません。 **中間支払いプラットフォーム**に接続するだけで、このプラットフォームは対応する支払い機関と統合し、契約、取得、決済を処理し、[charge コールバック API](api/charge-callback.md) を通じて支払い結果を報告します。

> 中間支払いプラットフォームは**このプロジェクトの一部ではありません。オペレーターは自分で開発する (または独自のシステムを使用する) 必要があります**。導入したら、「リチャージ サイト」に登録し、ドメイン認証を完了してリチャージ エントリ ポイントとして使用します。ここでのリチャージ サイトは、決済機関そのものではなく、中間プラットフォームです。支払い資格、手数料、決済およびコンプライアンスは、運営者、支払い機関および中間プラットフォームによって合意され、負担されます。

   - 通貨
   - 為替レート
3. 保存;
4. サイトを検証します (HTTP ファイルまたは DNS 検証)。

### 12.2 リチャージ注文

   - タイプ（金額、プラン、トラフィックアドオン）
   - 額面・プラン
   - 有効期限
3. または、一括で生成します。
   - 数量（1000個まで）
   - カード番号のプレフィックス
   - カード番号の形式

### 12.4 残高管理

## 25. オペレーションの拡張機能

「オペレーション拡張機能」(`/client-ext`) は、紹介マーケティング、手数料、引き出しを構成します。
「法的文書」(`/legal-documents`) は、ポータル側の契約を維持します。

### 25.1 紹介とコミッション

- **リベート設定**: リベート率 (招待者の最初の支払いの割合、`0` = 無効)、コミッション モード (初回購入のみ / すべての購入)、最低出金金額 (出金をリクエストするには、コミッション残高がこの金額に達する必要があります)
- **招待コード**: 有効にすると、登録には招待コードが必要になります。コードの長さ、有効期限、最大使用量 (`0` = 無制限) を設定し、コード リストを生成/表示します
- **撤回レビュー**: 保留中/承認/拒否でフィルタリングします。処理メモを追加し、支払い方法とウォレットアドレスを記録します
- **紹介記録**: 招待者、招待者、コミッション金額およびコミッションステータス

### 25.2 法的文書

- 「プライバシー ポリシー」と「サービス利用規約」を別々に管理し、ロケールごとに 1 つの Markdown ドキュメントをライブ プレビューで管理します。
- 各ドキュメントでは、組み込みページの代わりに外部 URL を使用できます。空の場合、組み込みページ URL が使用されます (ページ上でコピー可能)。
- ポータルには現在のロケールのバージョンが表示され、見つからない場合はデフォルトのロケールに戻ります。

## 26. よくある質問

### 26.1 パネルが起動しない

- ポートがすでに使用されているかどうかを確認する
- `.env`が有効であることを確認してください
- ログを確認してください: `journalctl -u corefusion -f`; systemd、`tail -f <install-dir>/data/logs/panel.log`なし

### 26.2 ノードがオフラインである

- エージェントが実行されていることを確認します: `systemctl status corefusion-agent`
- ネットワーク接続を確認する
- ファイアウォール ルールを確認します (ポート `18443`)。

### 26.3 証明書の発行に失敗する

- DNSの解像度を確認する
- ポート 80 が到達可能であることを確認する
- DNSプロバイダー構成を確認してください
- 証明書ログを確認する

### 26.4 サブスクリプションが機能しない

- 購読リンクを確認してください
- ノードがオンラインであることを確認します
- コアプロセスが実行されていることを確認します
- ファイアウォールルールを確認する

### 26.5 リチャージコールバックが失敗する

- コールバック URL を確認してください
- サイトキーが一致していることを確認してください
- IP許可リストを確認してください
- 注文履歴を確認する

### 26.6 ポータル ページにアクセスできない

- ポータルポートが開いているか確認してください
- ポータルのパス構成を確認してください
- **重要**: リバース プロキシがポータル ドメインをメイン パネル ポートではなく、**ポータル エンジン ポート**に転送していることを確認してください。間違ったポートに転送すると、ポータルではなく空白のページまたはパネルが表示されます。プロキシ サイト レコードの `upstream` / `local_port` を確認します。
- `http://<portal-domain>:<portal-port>` を直接開いて、ポータル エンジン自体を確認します。
- リバースプロキシ構成を確認してください
- ポータルのログを確認する

## 付録

### A. デフォルトのポート

| 港 | 目的 |
|------|---------|
| セットアップ ウィザードによって割り当てられます (デフォルトではランダムな空きポート) | 管理パネル（変更可能） |
| 18443 | エージェント gRPC (変更可能) |
| 0 (デフォルトでは無効) | 専用のサブスクリプション エンジン ポート (空、または `0` がメイン ポートを共有) |
| 0 (デフォルトでは無効) | 専用ポータル エンジン ポート (空、または `0` がメイン ポートを共有) |
| 80 / 443 | リバースプロキシ (Caddy / Nginx) HTTP / HTTPS |

### B. デフォルトのパス

| パス | 目的 |
|------|---------|
| `/` | 管理パネル (専用ポータル エンジンが構成されていない場合、ポータルは `/` にも存在します) |
| `/sub/:token` | サブスクリプションの取得 (専用のサブスクリプション ポートが構成されていない場合) |
| `/p` | ポータル ページ (専用ポータル ポートが構成されていない場合) |
| `/:token` | サブスクリプションのフェッチ (専用のサブスクリプション ポートを使用、`/sub` プレフィックスなし) |

### C. コマンドラインツール

パネル バイナリは次のサブコマンドをサポートしています (引数なしでサーバーが起動します)。

```bash
# Start the panel (same as ./corefusion server)
./corefusion

# Run database migrations
./corefusion migrate

# Non-interactive init / reset init state (see 3.4, 3.5)
./corefusion init --help
./corefusion reset-init

# Offline administration (when you cannot sign in)
./corefusion admin reset-password -u admin -p 'new-password'
./corefusion admin 2fa reset -u admin
./corefusion admin list

# Version / help
./corefusion version
./corefusion help
```

> systemd では、`systemctl restart corefusion` および `journalctl -u corefusion -f` を使用します。なしで
> systemd (コンテナーなど)、古いプロセスを停止し、`nohup` で再起動すると、ログが
> `data/logs/panel.log`で。

## v0.13.0-rc.1 の変更点

- **パネルのオンライン更新**: 「システム設定 → パネル更新」でバージョン選択（`pre` は
  プレリリース）、更新、タスク履歴、直前のバイナリへのロールバックが可能。
- **Agent のオンライン更新**: ノード詳細の「Agent 更新」から、パネル内のバイナリまたは
  GitHub Releases を使用。旧バージョンから更新したノードは初回接続時に
  `update.public_key`（0600）を自動で受け取り、以降 ed25519 署名を検証。
- **WAF 同期**: 最終同期時刻を `waf.github_source.last_sync` に保存し、再起動しても
  タイマーを初期化しない。`0 3 * * *` は `panel.timezone`（既定 Asia/Shanghai）の 03:00 に
  実行。逃した実行は起動約 15 秒後に補完。
- **WAF ホワイトリスト**: パネル転送ドメインは `whiteurl.rule` を自動維持。URL/引数/POST
  検査は管理 API のみスキップするため、`http://127.0.0.1:18081` のような決済サイトも
  SSRF ルールで遮断されない。
- **クォータポリシー**: 更新時に加算 / 期限切れで消去 / 更新時にリセット（バリアントは
  プランを継承可）。「毎月」では毎時チェックして使用量を 0 に。
- **決済サイト**: 有効/無効の切り替えでキーや決済方法は変わらない。チャージ注文は
  種別で絞り込み、CSV 出力が可能。
- **ポータル**: 「チャージ」は有効な決済サイトによるオンライン決済とカード利用に対応。
  サイト未設定時はカードのみ表示。
