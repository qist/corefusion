## 1. Обзор системы

CoreFusion — это многопротокольная панель управления прокси, поддерживающая VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC и другие, с управлением узлами, доставкой подписки, управлением клиентами, выставлением счетов, сертификатами и цепочками прокси.

### 1.1 Основные функции

| Модуль | Описание |
|--------|-------------|
| Мультипротокольный | VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, WireGuard и т. д. |
| Многоядерный | Xray-core и sing-box (Hysteria2/TUIC и другие протоколы QUIC, работающие на sing-box) |
| Многоузловой | Пять типов узлов: автономный, зеркальный, активный/резервный, цепочка входа, цепочка выхода. |
| Доставка подписки | Несколько форматов подписки, конечные точки и управление форматами |
| Биллинг | Шаблоны планов, карты пополнения баланса, заказы, комиссия реселлера |
| Сертификаты | Выдача Let's Encrypt, проверка DNS-01/HTTP-01, распространение сертификата |
| Привязанный прокси | Балансировка нагрузки с несколькими выходами, регистрация внешних узлов, цепная маршрутизация |
| Квоты на трафик | Ежемесячный мониторинг трафика для каждого узла, автоматическая приостановка, сброс журналов |
| Портал | Визуальный редактор портала, многоязычный, пользовательские шаблоны |
| Уведомления | Электронная почта и Telegram, шаблоны и трансляции |

### 1.2 Архитектура

- **Бэкэнд**: Вперёд, gRPC
- **Фронтенд**: Vue 3 + Element Plus
- **База данных**: SQLite (по умолчанию) / MySQL / PostgreSQL.
- **Прокси**: обратный прокси-сервер Caddy/Nginx.
- **Порт панели**: назначается мастером настройки (по умолчанию произвольный свободный порт; обычно выбирается 8080)
- **Порт агента gRPC**: 18443 по умолчанию.

## 2. Установка

### 2.1 Поддерживаемые среды

| Товар | Поддержка |
|------|---------|
| Распределения | Debian/Ubuntu, RHEL/CentOS/Rocky/AlmaLinux/Fedora, Alpine, Arch, openSUSE |
| Архитектуры ЦП | Официальные двоичные файлы: `amd64`, `arm64`; исходные сборки также поддерживают `armv7`, `armv6`, `386`, `ppc64le`, `s390x`, `riscv64`, `loong64`. |
| Менеджер по обслуживанию | systemd (рекомендуется); возвращается к `nohup` в контейнерах или других средах без systemd. |
| Память/диск | ≥ 1 ГБ/≥ 10 ГБ (база данных, сертификаты, журналы и основные двоичные файлы находятся в каталоге данных) |
| Порт панели | выбранный в мастере настройки (по умолчанию произвольный свободный порт; `8080` и подобные подходят) |
| Агент gRPC | `18443` по умолчанию |

Внешние команды среды выполнения устанавливаются автоматически установщиком (`scripts/install.sh` и сценарий установки агента, созданный панелью; пропустите с помощью `--no-deps` / `CF_SKIP_DEPS=1`):

| Цель | Пакет |
|---------|---------|
| Брандмауэр/ограничение скорости/маркировка параллелизма | `nftables` (`nft`) |
| Формирование трафика, ссылки и сокеты | `iproute2` (`tc` / `ip` / `ss`) |
| Резервный вариант, когда nft недоступен | `iptables` (`iptables-nft` на EL8+, `iptables` на EL7) |
| Отслеживание соединения | `conntrack-tools` (`conntrack`) |
| Загрузить `nf_conntrack` / `ifb` | `kmod` (`modprobe` / `lsmod`) |
| Обнаружение и очистка процессов | `procps` (`pgrep` / `pkill`) |
| Проверка портов/параметры DH | `lsof` / `openssl` |
| Создание пользователя прокси | `shadow-utils` (Debian `passwd`, Alpine/Arch `shadow`) |
| Загрузки и архивы | `curl` / `ca-certificates` / `tar` / `gzip` / `xz` |

> Отсутствие `nft`/`tc` влияет только на функции ограничения скорости и брандмауэра; панель все равно запускается.
> Сначала запустите `--cpu-info`, чтобы увидеть, как определяется среда и какие пакеты отсутствуют.

### 2.2 Однолинейная установка (рекомендуется)

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh -o install.sh
sudo bash install.sh
```

Или перенаправьте его напрямую (без взаимодействия, без дополнительных флагов):

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash
```

Скрипт будет:

1. Определите дистрибутив, архитектуру ЦП и libc, затем установите базовые пакеты и зависимости времени выполнения;
2. Загрузите `corefusion-linux-<arch>` из выпусков GitHub и сверьте его с соответствующим `.sha256`;
3. Установите `/opt/corefusion` и создайте `data/{sqlite,certs,logs,runtime}`;
4. Напишите только заполнитель `.env` с `SAFE_PATHS=data` — без конфигурации базы данных — поэтому при первом запуске происходит вход в мастер настройки (полный `.env` генерируется мастером);
5. Установите и запустите службу systemd (или запустите под `nohup`, когда systemd недоступен);
6. Подождите, пока все будет готово, затем распечатайте настройки URL, токены и пути к каталогам.

Пример вывода:

```text
==================================================================
 CoreFusion installation complete
------------------------------------------------------------------
 Install dir : /opt/corefusion
 Data dir    : /opt/corefusion/data
 Binary      : /opt/corefusion/corefusion
 Logs        : journalctl -u corefusion -f
------------------------------------------------------------------
 Setup wizard : http://<server-ip>:<random-port>/init?init_token=<token>
 Setup token  : <token>
 Valid for    : 2 hours (see startup log)
 Note         : the token is shown once; after setup this port closes and the panel switches to its normal port.
==================================================================
```

Если панель прослушивает только `127.0.0.1` (например, через обратный прокси-сервер), сценарий печатает команду туннеля SSH вместо недоступного URL.

> Потеряли жетон? Прочтите журнал запуска еще раз: `journalctl -u corefusion -n 50 --no-pager`.
> (без systemd: `tail -n 50 /opt/corefusion/data/logs/panel.log`).

### 2.2.1 Многоязычный вывод

Установщик включает четыре языка пользовательского интерфейса: упрощенный китайский, английский, персидский (فارسی) и русский (Русский). Он автоматически определяет систему `LANG`, или вы можете выбрать явно:

```bash
# English
sudo bash install.sh --lang en

# Persian via environment variable
sudo CF_LANG=fa bash install.sh

# Pass options through a pipe
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash -s -- --lang ru
```

Поддерживаемые значения: `zh`/`en`/`fa`/`ru`; `--lang=ru` также принимается. Неподдерживаемое явное значение не соответствует списку доступных языков.

### 2.3 Закрепление версии/зеркала/автономная установка

```bash
# Pin a version
sudo bash install.sh --version v0.13.1

# GitHub download mirror (used as a URL prefix)
sudo bash install.sh --mirror https://ghproxy.net --version latest

# Use a local binary (offline / intranet / pre-built)
sudo bash install.sh --local ./dist/corefusion-linux-arm64

# Explicit target architecture
sudo bash install.sh --arch arm64 --local ./corefusion-linux-arm64
```

> Без `--version` сценарий использует новейшую запись в списке выпусков GitHub.
> Большинство выпусков являются предварительными, поэтому конечная точка `/releases/latest` не используется.
>
> Официальные выпуски предоставляют только `amd64`/`arm64`; используйте `--source` или кросс-скомпилированный двоичный файл с `--local` для других архитектур.

### 2.4 Сборка из исходного кода

```bash
sudo bash install.sh --source --version v0.13.1
```

`--source` клонирует репозиторий (или использует существующую проверку, когда в нем находится скрипт) и запускает `make panel`. Версии Toolchain выбираются для каждой среды:

| Зависимость | Выбор |
|------------|-----------|
| Иди | Чтение из `toolchain`/`go` в `go.mod` (в настоящее время **Go 1.27+**); если версия системы слишком старая, соответствующая цепочка инструментов загружается в `<install-dir>/.toolchain`. |
| Узел | **Узел 22 LTS** по умолчанию (для Vite требуется ≥ 18); соответствующая официальная сборка загружается при необходимости |
| Узел (glibc < 2.28) | Использует сборку `unofficial-builds` glibc-217 (например, CentOS 7). |
| Узел (Альпийский/мусл) | Использует дистрибутив `nodejs`/`npm`. |

Переопределения:

```bash
# Force Go / Node versions
sudo CF_GO_VERSION=1.27.5 CF_NODE_MAJOR=22 bash install.sh --source

# Go toolchain mirror (default https://go.dev/dl)
sudo CF_GO_MIRROR=https://golang.google.cn/dl bash install.sh --source
```

Ручная сборка (разработка/отладка):

```bash
git clone https://github.com/qist/corefusion.git
cd corefusion

# Frontend + panel for the current architecture; the frontend is embedded via go:embed
make panel

# Cross-compile
make panel-linux-amd64
make panel-linux-arm64
```

> `go build ./...` не создает двоичный файл. Создайте панель с помощью
> `go build -o corefusion ./cmd/corefusion/` или `make panel`.

### 2.5 Флаги установщика

| Флаг | Описание |
|------|-------------|
| `-d, --dir <PATH>` | Каталог установки, по умолчанию `/opt/corefusion` |
| `-v, --version <TAG>` | Панельная версия, напр. `v0.13.1`; по умолчанию `latest` |
| `--binary` | Используйте двоичный файл выпуска GitHub (по умолчанию). |
| `--source` | Сборка из исходного кода и подготовка соответствующего Go/Node. |
| `--local <FILE>` | Используйте локальный двоичный файл (автономная установка) |
| `--arch <ARCH>` | Целевая архитектура: `amd64` / `arm64` / `armv7` / `armv6` / `386` / `ppc64le` / `s390x` / `riscv64` / `loong64` |
| `--mirror <URL>` | GitHub префикс загрузки, например. `https://ghproxy.net` |
| `--repo <URL>` | Репозиторий исходного кода, по умолчанию `https://github.com/qist/corefusion.git` |
| `--ref <REF>` | Исходная ветка/тег; по умолчанию `--version`, в противном случае `main` |
| `--no-deps` | Пропустить установку системных зависимостей |
| `--no-start` | Установить и записать сервисный файл не запуская |
| `--cpu-info` | Распечатайте обнаружение среды и отсутствующие зависимости, затем выйдите. |
| `--lang <LANG>` | Язык вывода: `zh` / `en` / `fa` / `ru` (по умолчанию: системный `LANG`) |
| `--uninstall` | Остановите службу и удалите программу (сохраняет данные и `.env`) |
| `--purge` | С помощью `--uninstall` также удалите каталог данных и `.env`. |

> Официальные выпуски поставляются только с двоичными файлами `amd64`/`arm64`. Для других архитектур требуется `--source`.
> в противном случае загрузка возвращает 404.

Связанные переменные среды:

| Переменная | Цель |
|----------|---------|
| `CF_GO_VERSION` | Переопределить версию Go, необходимую для сборок исходного кода. |
| `CF_NODE_MAJOR` | Переопределить основную версию узла (по умолчанию 22). |
| `CF_GO_MIRROR` | Зеркало загрузки Go Toolchain |
| `CF_SKIP_DEPS` | Установите значение `1` в сценарии установки агента, чтобы пропустить установку зависимостей. |
| `CF_LANG` | Переопределить язык вывода установщика (тот же, что и `--lang`) |

### 2.6 Структура каталога

```text
/opt/corefusion/
├── corefusion                 # panel binary
├── corefusion.bak             # previous version (when upgrading)
├── .env                       # environment file (0600, generated by the setup wizard)
├── .env.secret                # encryption key file (0600, generated on first start)
├── .toolchain/                # Go / Node downloaded for source builds
└── data/                      # data directory (SAFE_PATHS)
    ├── sqlite/app.db          # default SQLite database
    ├── certs/                 # certificates and keys
    ├── logs/                  # runtime logs (without systemd)
    ├── runtime/               # core runtime config and state
    ├── binaries/              # downloaded xray / sing-box cores
    └── proxy/                 # proxy (Caddy/Nginx) sites and config
```

> Установщик создает только `sqlite/`, `certs/`, `logs/` и `runtime/`; `binaries/`, `proxy/`, `rules/` и другие создаются панелью или при установке ядер.
> Каталог данных происходит от `SAFE_PATHS` в `.env` и может быть абсолютным путем. Изменение каталога установки не приводит к перемещению существующих данных.

### 2.7 Управление услугами

systemd (большинство дистрибутивов):

```bash
systemctl status corefusion --no-pager
systemctl restart corefusion
systemctl stop corefusion
journalctl -u corefusion -f          # follow logs
journalctl -u corefusion -n 100      # last 100 lines
```

Без systemd (контейнеры и т.п.):

```bash
cd /opt/corefusion && ./corefusion            # foreground (debugging)
cd /opt/corefusion && setsid nohup ./corefusion >> data/logs/panel.log 2>&1 &
tail -f data/logs/panel.log
```

> Без systemd процесс при загрузке не запускается; перезапустите его вручную после перезагрузки (или перезапустите установщик).

### 2.8 Обновление и удаление

Обновление (сохраняет данные и конфигурацию):

```bash
sudo bash install.sh --version <new-version>
```

Сценарий останавливает службу, создает резервную копию старого двоичного файла под именем `corefusion.bak`, заменяет его и перезапускается. Существующие `.env` и `data/` остаются нетронутыми.

Удалить:

```bash
# Remove the program only; keep data and .env
sudo bash install.sh --uninstall

# Also remove the data directory and .env (irreversible)
sudo bash install.sh --uninstall --purge
```

### 2.9 Файл среды (.env)

Полный `.env` **создается мастером установки** при сохранении конфигурации (DSN базы данных, каталог данных, секреты, порты, домены).

При новой установке установщик записывает только этот заполнитель, чтобы панель не приняла существующий `data/` за инициализированную установку и не пропустила мастер:

```env
SAFE_PATHS=data
```

> Если полная конфигурация (`.env` с `CF_DB_DSN`) уже существует, программа установки никогда не перезаписывает ее, и мастер больше не появляется.
> Более поздние изменения, внесенные вручную в `.env`, вступят в силу после перезагрузки.

#### Каталог данных

```env
SAFE_PATHS=data                       # relative to the install directory
# SAFE_PATHS=/srv/corefusion-data     # or an absolute path
```

#### База данных

`CF_DB_DSN` обнаруживается по префиксу:

| Префикс | База данных |
|--------|----------|
| не установлен или пустой путь | SQLite (по умолчанию) |
| `sqlite://` | SQLite (явный) |
| `mysql://` | MySQL |
| `postgres://` / `postgresql://` | PostgreSQL |

`CF_DB_TYPE` является необязательным и имеет приоритет над обнаружением (`sqlite`/`mysql`/`postgres`).

> **Зашифрованные пароли**: DSN MySQL/PostgreSQL, записанные панелью (мастер настройки/переключатель базы данных)
> хранятся в `.env` как `enc:...` (AES-256-GCM, ключ `CF_SECRET_ENCRYPTION_KEY`).
> Они расшифровываются при чтении; Уведомления о доставке в виде открытого текста, написанные вручную, по-прежнему работают.

**SQLite (по умолчанию)**

```env
# Bare path (detected as SQLite)
CF_DB_DSN=data/sqlite/app.db

# Or explicit sqlite:// prefix
CF_DB_DSN=sqlite:///opt/corefusion/data/sqlite/app.db
```

**MySQL**

```env
# Format: mysql://user:password@tcp(host:port)/dbname?params
CF_DB_DSN=mysql://corefusion:password@tcp(127.0.0.1:3306)/corefusion?charset=utf8mb4&parseTime=True&loc=Local
```

**PostgreSQL**

```env
# Format: postgres://user:password@host:port/dbname?params
CF_DB_DSN=postgres://corefusion:password@127.0.0.1:5432/corefusion?sslmode=disable
```

#### Пул соединений (дополнительно, MySQL/PostgreSQL)

```env
CF_DB_MAX_OPEN_CONNS=100
CF_DB_MAX_IDLE_CONNS=10
```

#### Другие общие переменные

| Переменная | Описание |
|----------|-------------|
| `JWT_SECRET` | Ключ подписи для токенов входа; генерируется при первом запуске при отсутствии |
| `CF_SECRET_ENCRYPTION_KEY` | Ключ для шифрования конфиденциальных настроек (AES-256-GCM); генерируется при отсутствии |
| `CF_INITIAL_ADMIN_PASSWORD` | Начальный пароль администратора (необязательно; по умолчанию случайный и печатается один раз) |
| `CF_NETWORK_TRAFFIC_ACCOUNTING` | Установите значение `0`, чтобы отключить учет трафика на основе iptables (включено по умолчанию). |
| `CF_NETWORK_TRAFFIC_TABLE` | таблица iptables, используемая для учета трафика, по умолчанию `corefusion` |

> **Ключ шифрования находится в `.env.secret`**: при первом запуске `CF_SECRET_ENCRYPTION_KEY` записывается в `.env.secret` (0600, тот же каталог, что и `.env`) вместо `.env`; устаревший ключ в `.env` переносится автоматически. Создайте резервную копию этого файла отдельно — его потеря сделает нерасшифрованным каждое значение `enc:`.

> Доверенные обратные прокси-серверы для разрешения реальных IP-адресов клиентов больше не настраиваются через переменные среды;
> они хранятся как `panel.trusted_proxies` в **Настройки → Сеть**.

> И `.env`, и `.env.secret` содержат секреты; панель при запуске ужесточает свои разрешения для `0600`. Никогда не совершайте их.

### 2.10 Docker (необязательно, создайте свой образ)

Репозиторий **не** отправляет Dockerfile. Если вы помещаете его в контейнер, напишите свой собственный образ. Ссылочный вызов:

```bash
docker run -d \
  --name corefusion \
  -p 8080:8080 \
  -p 18443:18443 \
  -v /opt/corefusion/data:/app/data \
  -v /opt/corefusion/.env:/app/.env \
  <your-image>
```

> Контейнеры обычно не имеют привилегий systemd и `nft`, поэтому функции ограничения скорости/брандмауэра работать не будут.
> Рабочий каталог должен соответствовать базе относительного `SAFE_PATHS`.

## 3. Начальная конфигурация

Если при первом запуске `.env` не имеет действующего `CF_DB_DSN`, панель еще **не** обслуживает пользовательский интерфейс администратора. Это начинает
**Мастер настройки** на случайном порту в диапазоне 18000–18999 с одноразовым токеном, затем перезапускается как обычная панель после сохранения.

### 3.1 Откройте мастер настройки

1. Скопируйте «мастер установки» URL из вывода программы установки; или
2. Читаем лог на сервере:

```bash
journalctl -u corefusion -n 50 --no-pager | grep -A2 'setup wizard'
```

```text
CoreFusion first start - setup wizard
  URL   : http://<ip>:<port>/init?init_token=<token>
  Token : <token>
  Valid : 2h0m0s
```

3. Откройте URL в браузере (он уже содержит `init_token`, поэтому ввод вручную не требуется).

> По умолчанию сеанс мастера завершается через **2 часа**. Если срок его действия истек или панель перезапускается, получите новую.
> Не делитесь токеном. После завершения настройки этот порт закрывается, и остается только обычный порт панели.

### 3.2 Шаги мастера

Мастер имеет 8 шагов. Вы можете вернуться в любое время; ничего не фиксируется до последнего сохранения.

| Шаг | Содержание |
|------|---------|
| 1. База данных | SQLite / MySQL / PostgreSQL |
| 2. Каталог данных | Написано `SAFE_PATHS` в `.env` |
| 3. Ключи шифрования | `JWT_SECRET` и `CF_SECRET_ENCRYPTION_KEY` |
| 4. Ядра | Какие прокси-ядра установить |
| 5. Прокси | Нет / Nginx / Caddy |
| 6. Сайты и домены | Порты, веб-путь, учетная запись администратора, валюта, часовой пояс, домены |
| 7. Сертификат HTTPS | Отключено/загрузка/ACME |
| 8. Резюме | Просмотрите, скачайте `.env`, сохраните и перезапустите. |

#### Шаг 1: База данных

- **SQLite (рекомендуется локальный файл)**: оставьте путь пустым, чтобы использовать `<data-dir>/sqlite/app.db`.
- **MySQL / PostgreSQL**: хост, порт, пользователь, пароль, имя базы данных; PostgreSQL также поддерживает `disable`/`require`/`verify-full`.
- Нажмите «Проверить соединение» для подтверждения. Сохранение также проверяет это. Недостающая база данных создается автоматически (создайте ее вручную, если в учетной записи отсутствует `CREATE`).
- DSN (включая пароль) шифруется перед записью в `.env`.

#### Шаг 2: Каталог данных

Хранит базу данных, сертификаты, журналы, основные двоичные файлы и многое другое; это `SAFE_PATHS` в `.env`. По умолчанию `data`.
(относительно каталога установки); разрешен абсолютный путь. **Не меняйте его позже** или панель
не найдет существующую базу данных и сертификаты.

#### Шаг 3. Ключи шифрования

- `JWT_SECRET`: подписывает токены входа.
- `CF_SECRET_ENCRYPTION_KEY`: шифрует конфиденциальные настройки (пароль базы данных, учетные данные DNS, карты пополнения счета и т. д.).
- По умолчанию оба генерируются случайным образом; используйте «Регенерировать», чтобы получить новые значения. **Изменение `CF_SECRET_ENCRYPTION_KEY` делает ранее зашифрованные данные нечитаемыми** — сделайте резервную копию.

#### Шаг 4: Ядра

Выберите ядра прокси для установки:

- **Xray**: VLESS / VMess / Trojan / Shadowsocks и т. д.;
- **sing-box**: поддерживает Hysteria2/TUIC и другие протоколы QUIC.

После сохранения и перезапуска панель автоматически загрузит и установит их. Проверьте версии и статус в разделе «Протоколы». Вы также можете установить их позже.

#### Шаг 5: Прокси

- **Нет**: панель обслуживает клиентов напрямую (обработайте TLS самостоятельно).
- **Nginx / Caddy**: панель управляет обратным прокси-сервером и хостингом сертификатов; выберите один.

Если выбран прокси-сервер, панель обычно прослушивает только `127.0.0.1`, а прокси-сервер обслуживает внешний мир.

#### Шаг 6. Сайты и домены

| Поле | Описание |
|-------|-------------|
| Прослушать адрес | Производится автоматически: прокси → `127.0.0.1`; нет прокси с сертификатом → `0.0.0.0`; в противном случае → `127.0.0.1` |
| Порт панели | Случайный свободный порт по умолчанию; измените его, если хотите (например, 8080) |
| Порт подписки | Необязательно; `0` использует общий порт панели |
| Портальный порт | Необязательно; `0` использует общий порт панели |
| Веб-путь | Путь к интерфейсу администратора, по умолчанию `/`; API всегда `/api/v1` |
| Имя пользователя/пароль администратора | Случайно по умолчанию; **пароль отображается в сводке только один раз** — сохраните его |
| Режим доступа | «Домен» или «IP» |
| Валюта/часовой пояс по умолчанию | Валюта по умолчанию для пополнения карт и балансов; часовой пояс панели и журнала прокси (например, `Asia/Shanghai`) |
| Добавить в обратный прокси | Когда прокси и домены настроены, добавьте к прокси домены панели/подписки/портала за один раз. |

При вводе доменов прописываются соответствующие настройки (домен обратного вызова, конечная точка подписки, общий домен).

#### Шаг 7: Сертификат HTTPS

| Источник | Описание |
|--------|-------------|
| Отключить HTTPS | Панель/портал/подписки обслуживаются через HTTP (небезопасно); с обратным прокси-сервером вы можете добавить TLS на стороне прокси позже |
| Загрузить сертификат | Вставьте сертификат PEM и закрытый ключ PEM (только режим доступа к домену) |
| ACME | Выдает сертификат при отправке этого шага; поддерживает доменные и IP-сертификаты |

Варианты ACME:

- **CA**: Let's Encrypt, Let's Encrypt (промежуточный), ZeroSSL, Google общедоступный центр сертификации;
- **Цель**: настроенный домен или общедоступный IP-адрес (IP-сертификаты поддерживаются только Let's Encrypt);
- **Задание**: `HTTP-01` (требуется порт 80) или `DNS-01` (подстановочные знаки, без порта 80; выберите поставщика DNS и введите учетные данные);
- **Тип/размер ключа**: ECC 256/384 или RSA 2048/3072/4096;
- **Google Публичный ЦС**: требуется EAB; введите идентификатор ключа/HMAC вручную или используйте учетную запись службы GCP.

> IP-сертификаты автоматически определяют общедоступный IPv4/IPv6 хоста. За прокси-сервером обнаруженный адрес принадлежит хосту, а не выходу прокси.
> Сертификаты домена также можно выдать позже в разделе «Сертификаты».

#### Шаг 8: Резюме

Показывает базу данных, каталог данных, ядра, прокси, порты, учетную запись администратора, домены и ключи `.env` (секреты замаскированы) и предоставляет:

- **Загрузить .env**: сохраните копию конфигурации;
- **URL-адреса доступа**: конечные URL-адреса панели/подписки/портала; HTTP помечен как небезопасный.

Нажмите «Сохранить и перезапустить», чтобы записать базу данных и `.env`; панель перезапускается в обычном режиме.

### 3.3 После установки

- Служба перезапускается, и в журнале запуска печатается окончательный адрес прослушивания;
- Войдите в систему с учетной записью администратора, получите доступ к URL и веб-пути из сводки;
- Если пароль утерян, сбросьте его в автономном режиме с помощью `./corefusion admin reset-password`.

### 3.4 Неинтерактивная настройка CLI

Для автоматизированных или автономных серверов напишите конфигурацию и отметьте установку как завершенную:

```bash
cd /opt/corefusion
./corefusion init \
  --db-type sqlite \
  --data-dir /opt/corefusion/data \
  --admin-username admin \
  --admin-password 'change-me-strong-password' \
  --listen-port 8080 \
  --proxy-type caddy \
  --cores xray,singbox \
  --panel-domain panel.example.com \
  --tls-mode acme --tls-domain panel.example.com --tls-email you@example.com
```

Общие флаги:

| Флаг | Описание |
|------|-------------|
| `--db-type` / `--db-host` / `--db-port` / `--db-user` / `--db-password` / `--db-name` | Настройки базы данных |
| `--data-dir` | Каталог данных; по умолчанию `SAFE_PATHS` или `./data` |
| `--listen-port` / `--subscription-port` / `--portal-port` / `--web-path` | Порты и веб-путь (по умолчанию произвольный свободный порт) |
| `--admin-username` / `--admin-password` | Учетная запись администратора (случайный пароль печатается один раз, если его опустить) |
| `--proxy-type` | `none` / `nginx` / `caddy` |
| `--cores` | Ядра для установки, через запятую: `xray,singbox`. |
| `--panel-domain` / `--subscription-domain` / `--portal-domain` | Домены (прописаны в настройках и добавлены в обратный прокси) |
| `--tls-mode` | `none` / `self_signed` / `acme` |
| `--tls-domain` / `--tls-email` / `--tls-challenge` / `--tls-key-type` / `--tls-key-bits` | Параметры сертификата (для `--tls-challenge` по умолчанию — `http-01`; для `dns-01` требуется `--tls-dns-channel` или `--tls-dns-provider`) |
| `--tls-ip-cert` | Выдать сертификат для обнаруженного общедоступного IP-адреса (только Let’s Encrypt) |
| `--acme-provider` | `lets_encrypt` / `lets_encrypt_staging` / `zerossl` / `google` |
| `--currency` / `--timezone` | Валюта/часовой пояс по умолчанию |

Полный список: `./corefusion init --help`. Затем запустите службу:

```bash
systemctl restart corefusion
```

### 3.5 Повторный запуск мастера установки

Чтобы начать заново (удаляет `.env` и метки настройки, **сохраняет данные**):

```bash
cd /opt/corefusion
./corefusion reset-init      # type RESET to confirm
systemctl restart corefusion
```

Затем используйте новый URL и токен из журнала запуска.

> Повторная инициализация сбрасывает учетную запись администратора и веб-путь. Бизнес-данные в старой базе данных остаются, но вам может потребоваться заново создать учетную запись для входа.
>
> `reset-init` удаляет весь `.env` (включая `SAFE_PATHS`). **Если ваш каталог данных имеет пользовательский абсолютный путь**, восстановите `SAFE_PATHS` перед перезапуском, иначе панель будет выглядеть в `./data`:
>
> ```баш
> printf 'SAFE_PATHS=/srv/corefusion-data\n' > /opt/corefusion/.env
> ```

### 3.6 Безопасность после первого входа в систему

#### Изменить первоначальный пароль

1. Нажмите на имя пользователя в правом верхнем углу;
2. Выберите «Сменить пароль»;
3. Введите старый и новый пароли;
4. Нажмите «Сохранить».

#### Включить вход с динамическим кодом (2FA / TOTP)

> После включения учетная запись переключается на **вход с динамическим кодом**: статический пароль больше не принимается; только
> Шестизначный код из вашего приложения для аутентификации (или одноразовый код восстановления) работает. Это **заменяет** пароль для входа в систему — это
> не двухэтапная проверка «пароль+код».

1. Нажмите на имя пользователя в правом верхнем углу;
2. Выберите «Включить 2FA»;
3. Введите текущий пароль (только для подтверждения этого изменения);
4. Отсканируйте QR-код с помощью приложения-аутентификатора (Google Authenticator / 1Password и т. д.) или введите ключ вручную;
5. Введите 6-значный код, чтобы завершить включение;
6. **Сохраните коды восстановления немедленно** (можно загрузить); каждый код работает один раз.

Вход в систему после:

- После ввода имени пользователя поле пароля становится «6-значный код/код восстановления», а кнопка — «Войти с кодом»;
- Введите текущий код; **статический пароль больше нельзя использовать**;
- Коды восстановления одноразовые; восстановить их в разделе «Вход с динамическим кодом (2FA)», когда они закончатся (это аннулирует все старые коды).

Если аутентификатор утерян и коды восстановления исчерпаны, отключите 2FA в автономном режиме на сервере:

```bash
cd /opt/corefusion
./corefusion admin 2fa reset -u admin    # disables 2FA, clears the secret and recovery codes, revokes all sessions
```

> Единственный суперадминистратор, не имеющий ни аутентификатора, ни кодов восстановления, не может выполнить восстановление через веб-интерфейс и должен использовать приведенную выше команду.

#### Зарегистрируйте Passkey (необязательно)

1. Нажмите на имя пользователя в правом верхнем углу;
2. Выберите «Управление Passkey»;
3. Нажмите «Зарегистрировать новый Passkey»;
4. Заполните подсказку устройства.

> **Примечание**. Для ключей доступа требуется HTTPS или localhost, а домен должен быть внесен в список разрешенных.

## 4. Панель управления

На панели мониторинга отображается обзор кластера с несколькими узлами и состояние узла.

### 4.1 Что это показывает

- **Информация о системе**: имя хоста, версия ОС, время безотказной работы, процессор, память.
- **Трафик**: пропускная способность в реальном времени, общий трафик, ежемесячный тренд.
- **Работоспособность узлов**: количество онлайн/оффлайн/деградация, узлы с высокой нагрузкой
- **Оповещения**: автономные узлы, устаревшие узлы, скоро истечение срока действия сертификатов, предупреждения о квотах.
- **Ресурсы кластера**: среднее значение ЦП, памяти, диска и пропускной способности.

### 4.2 Действия

- Нажмите «Просмотреть подробности», чтобы открыть страницу сведений об узле.
- Нажмите карточку узла, чтобы увидеть ее текущий статус.
- Используйте фильтры, чтобы сузить список по статусу, типу или региону.

## 5. Управление узлами

Управление узлами является ядром CoreFusion и поддерживает несколько типов узлов.

### 5.1 Типы узлов

| Тип | Описание |
|------|-------------|
| Автономный (`standalone`) | Независимый основной узел |
| Зеркало (`mirror`) | Синхронизирует конфигурацию с целевого узла |
| Основной/резервный (`primary_backup`) | Партнерские узлы, которые переключаются друг на друга |
| Цепной вход (`chain_entry`) | Входной узел связанного прокси |
| Цепной выход (`chain_exit`) | Выходной узел связанного прокси |

### 5.2 Добавление узла

1. Откройте «Управление узлами»;
2. Нажмите «Добавить сервер»;
3. Заполните основные сведения:
   - Имя, например `HongKong-HK01`
   - Имя хоста: IP или домен
   - Регион, например `HK`, `JP`, `US`
   - Тип узла;
4. Установите порт агента (по умолчанию `18443`);
5. Выберите поддерживаемые ядра;
6. Нажмите «Сохранить».

### 5.3 Развертывание в один клик

1. После добавления узла выберите «Команда развертывания» в списке узлов (на странице сведений также предлагается
 «Команда установки Bootstrap»);
2. Скопируйте команду — она содержит одноразовый регистрационный токен (действителен в течение 24 часов, не использовать повторно);
3. Запустите его от имени пользователя root на удаленном узле; это выглядит так:

   ```bash
   bash <(curl -fsSL "http://<panel-host>:<panel-port>/api/v1/agent/install?id=<node-id>&token=<one-time-token>&port=<panel-port>")
   ```

4. Агент скачивает пакет, регистрируется в панели и запускается.

### 5.4 Детали узла

Щелкните узел, чтобы открыть страницу его сведений:

Центр протоколов настраивает параметры протоколов для основных процессов.

### 6.2 Модули конфигурации

Модули двух ядер различаются; на панели отображается набор, соответствующий выбранному ядру:

**Xray-ядро**

- **Журнал**: журнал доступа, журнал ошибок, режим вывода.

- **Входящие/исходящие**: протокол, транспорт, TLS
- **Транспорт**: WebSocket, gRPC, XHTTP и т. д. (TUN — это входящий протокол, а не транспорт).
- **TLS**: сертификаты, ALPN, отпечаток uTLS, ECH
- **Reality**: управление целями, пары ключей, короткие идентификаторы.

**sing-box**

- **Журнал**: уровень, временная метка, выходные данные.
- **NTP**: синхронизация времени
- **DNS**: серверы и правила DNS.
- **Маршрутизация**: исходящий трафик `final` по умолчанию, **Наборы правил**, **Правила**, преобразователь домена по умолчанию, сетевая стратегия и резервный вариант (см. 6.6).
- **Входящие/исходящие**: протокол, транспорт, TLS
- **Конечные точки**: WireGuard (включая конфигурации WARP), клиенты MASQUE и аналогичные; несколько могут сосуществовать и различаются `tag`

> Если включена опция «использовать системную сетевую интеграцию», **имя** конечной точки является именем интерфейса ядра:
> не более 15 символов, только буквы/цифры/`._-`. Слишком длинное или недействительное имя автоматически возвращается.
> до конечной точки `tag`. Новые конечные точки имеют префикс для каждого протокола (`wg-` / `ts-` / `oc-` / `ovpn-c-` /
> `ovpn-s-` / `mq-c-` / `mq-s-`), а устаревшие записи, такие как `WireGuard-xxxxxx`, отображаются нормализованными.
> как только редактор откроется.
- **Службы**: массив sing-box `services` верхнего уровня, например `hysteria-realm`, DERP или `resolved`.
- **Сертификаты/клиенты HTTP/сетевые пространства имен**: разделы JSON расширяются только при необходимости.
- **Экспериментальный**: `clash_api` и аналогичные; **в сгенерированную конфигурацию ничего не записывается, если она не включена**

> В sing-box 1.12 удалены поля маршрутизации `geosite`/`geoip`; Маршрутизация на основе географического положения теперь осуществляется
> `rule_set`. Сохранение старых полей приводит к тому, что ядро ​​не может декодировать конфигурацию (`unknown field`).

### 6.3 Входящая конфигурация

1. Выберите ядро и протокол;
2. Заполните основные сведения:
   - Тег
   - Слушать адрес и порт
   - Тип протокола
3. Установить параметры протокола (UUID, пароль и т.д.);
4. Выберите транспорт (TCP, WebSocket, gRPC и т. д.);
5. Настроить TLS (сертификат, ALPN);
6. Сохраните и примените к ядру.

> Новые входящие потоки прослушиваются на `::` по умолчанию (двойной стек на Linux, обрабатывающий как IPv4, так и IPv6).
> Меняйте его на `0.0.0.0` или конкретный адрес только тогда, когда вам нужно ограничить интерфейс.

Режимы порта «Использовать входящий порт» также предлагают **автоматическое создание правил разрешения брандмауэра**:
входящий редактор сначала проверяет брандмауэр узла, а затем обнаруживает firewalld/ufw/nftables/iptables
вы можете разрешить сохранение порта в соответствии с протоколом прослушивания (TCP/UDP).

- Переключение портов hy2/hysteria позволяет использовать как прослушиваемый порт, так и каждый динамический диапазон портов (например, `20000-30000`); несколько диапазонов разделяются запятыми;
- Разрешение является идемпотентным: существующее правило покрытия (диапазон портов/мультипорт) не создается повторно;
- Изменение порта отменяет старое правило, прежде чем разрешить новое; удаление входящего трафика, отключение переключения портов или переключение на Unix Socket/tun (без порта прослушивания) очищает его;
- Если включенный брандмауэр не обнаружен, отображается только подсказка и правила не записываются.

**Транспорт и поток**:

- `xtls-rprx-vision` работает только поверх необработанного TCP: с gRPC/XHTTP/WebSocket клиент полностью выходит из строя (sing-box: `initialize vision: not a valid supported TLS connection`) или не соглашается с проверкой потока сервера (`flow mismatch`). Панель удаляет видимость из любого входящего несырого/TCP при сохранении и при создании конфигурации времени выполнения;
- Транспорты sing-box доступны только по протоколу http / ws / quic / grpc / httpupgrade — **сырой TCP означает полное отсутствие транспорта**. Первая (пустая) запись раскрывающегося списка транспорта — это необработанный TCP; запись `type: "tcp"` заставляет ядро ​​отказываться от конфига.

### 6.3.1 Путь обратного прокси (Домен доступа → Front TLS → Путь обратного прокси)

Когда собственный транспортный путь входящего потока — `/`, но внешний nginx / caddy монтирует его под подпутем.
(например, `location /apps { proxy_pass http://127.0.0.1:8080/; }`), клиенты должны подключиться к `/apps` или
запрос никогда не достигает этого места — подписка все равно загружается, но узел не подключается.
Заполните **Путь обратного прокси** в разделе «Домен доступа → Front TLS»:

- Введите `/apps` или `/apps?ed=2560` (с ранними данными); подписки и ссылки общего доступа **заменяют** ими входящий транспортный путь;
- Применяется к ws, httpupgrade, xhttp и h2/http; транспорты без пути (raw/tcp, kcp) игнорируются;
- Он не зависит от того, где заканчивается TLS: путь по-прежнему применяется, когда Front TLS выключен (следует за ядром);
- В gRPC нет концепции префикса URL (путь клиента всегда `/{serviceName}/…`), поэтому путь **объединяется с именем службы**
(`/apps` + `svc` → `apps/svc`); обратный прокси-сервер должен удалить этот префикс в `grpc_pass`.

### 6.3.2 Маршрутизация на основе SNI (nginx vs Caddy)

Внешний TLS-слой распределяет соединения на `:443` по SNI из ClientHello: входы REALITY в центре протоколов
автоматически порождают правила, а сами правила можно задать вручную в «Управление прокси → SNI». Оба прокси умеют
разделять по домену; разница — в области действия PROXY protocol.

| | nginx (stream) | Caddy (layer4) |
|---|---|---|
| Область `proxy_protocol` | nginx из пакета панели (с патчем `stream_pp_var`): **для каждого SNI-правила**, v1 / v2 / выкл. Официальный или непатченный nginx: вся группа listen (уровень `listen`), для порта либо всё включено, либо всё выключено | Для каждого маршрута (`proxy ... { proxy_protocol v2 }`) |
| xray + sing-box на одном `:443` | Поддерживается после патча: REALITY xray получает v1/v2, правило sing-box — выкл. | Поддерживается: один SNI идёт в xray (PP v2), другой в sing-box (без PP) |
| Как достучаться до sing-box | После патча может делить `:443` с xray (PP для этого домена выкл.); иначе отдельный порт или отдельная группа listen без PP | Делит `:443` с xray, разделение по SNI |

Примечания:

- По умолчанию остаётся `v1` (прежний `proxy_protocol on`). Для каждого SNI-сайта можно выбрать `v1`, `v2` или выкл. `v2` —
  бинарный заголовок (28 байт для IPv4), короче текстового v1 (~50–60 байт); разница возникает один раз на соединение и
  практически незаметна.
- Панель через Agent выполняет `nginx -V` и ищет `NGX_STREAM_PP_VAR` (признак `stream_pp_var`), результат кешируется на
  60 секунд. Для непатченного nginx, при неудачной проверке или старом Agent выполняется откат на `proxy_protocol on` для
  всей группы (v1), а порождённые правила sing-box пропускаются (в логе `skipped N sing-box REALITY SNI rule(s)`);
  конфигурация, не проходящая `nginx -t`, не создаётся.
- sing-box REALITY / anytls не принимает заголовки PROXY, поэтому порождённые правила всегда выключены. Принудительные
  v1/v2 для такого домена ломают рукопожатие.
- За обратным прокси xray нужен PROXY protocol, чтобы видеть реальные IP и порт клиента (`sockopt.acceptProxyProtocol`);
  `realitySettings.xver` — это то, что xray отправляет в dest, и к этому отношения не имеет.
- `singbox_listen_port` в «Шаблоне Reality» — это **локальный TLS-эндпоинт** (dest для xray / handshake для sing-box),
  поддерживается обоими прокси и не связан с публичной SNI-маршрутизацией выше.

### 6.6 Маршрутизация и наборы правил sing-box

В «Центре протоколов» → sing-box → «Маршрутизация» есть две части: **Наборы правил** объявляют многоразовые.
файлы правил, а **Правила** определяют условия соответствия и исходящие сообщения. Правила оцениваются от
сверху вниз, и первый матч выигрывает.

#### 6.6.1 Наборы правил

| Поле | Описание |
|-------|-------------|
| тег | Идентификатор набора правил, на который ссылаются Rules; должен быть уникальным |
| Тип | `local` читает файл на узле; `remote` позволяет ядру загрузить его на `update_interval`. |
| Формат | `binary` для `.srs` (по умолчанию); `source` для исходного формата `.json` |
| Путь | Пути `local` относятся к каталогу данных узла; файлы в `data/rules/` используют `rules/xxx.srs` |
| URL | Скачать адрес для `remote`; `download_detour` выбирает исходящий трафик, используемый для загрузки (обычно `direct`). |

Наборы локальных правил (рекомендуется; сначала загрузите файлы в разделе «Ресурсы сервиса → Файлы правил»):

```jsonc
"route": {
  "rule_set": [
    { "type": "local", "tag": "geosite-cn", "format": "binary", "path": "rules/geosite-cn.srs" },
    { "type": "local", "tag": "geoip-cn", "format": "binary", "path": "rules/geoip-cn.srs" }
  ]
}
```

> Загрузить файл на панель недостаточно: сначала необходимо отправить набор правил `local` на панель.
> узлы («Push to all nodes»), чтобы файл существовал в `data/rules/` узла; иначе ядро
> не запускается, потому что файл не найден.

Наборы удаленных правил (узел должен иметь возможность доступа к URL):

```jsonc
{ "type": "remote", "tag": "geosite-openai", "format": "binary",
  "url": "https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-openai.srs",
  "download_detour": "direct", "update_interval": "1d" }
```

Когда вы выбираете локальный файл, тег получается из имени файла (`rules/geosite-cn.srs` →
`geosite-cn`); для удаленных комплектов он берется из конца URL. Формат также заполняется из
расширение (`.srs` → `binary`, `.json` → `source`). Производные значения можно свободно редактировать, и
значения, которые вы уже ввели, никогда не перезаписываются.

> `download_detour` устарел, начиная с sing-box 1.14, и будет удален в версии 1.16; это все еще
> работает в 1.15. В новых конфигурациях следует использовать `http_clients` верхнего уровня с
> Вместо этого `route.default_http_client`.

#### 6.6.2 Правила

| Поле | Матчи |
|-------|---------|
| `domain` | Точный домен |
| `domain_suffix` | Суффикс домена, включая субдомены |
| `domain_keyword` | Совпадение подстроки |
| `domain_regex` | Регулярное выражение |
| `ip_cidr` / `ip_is_private` | IP-адрес назначения |
| `source_ip_cidr` | Исходный IP-адрес |
| `port` / `port_range` | Порт назначения |
| `network` | `tcp` / `udp` |
| `rule_set` | Теги наборов правил для использования |
| `outbound` | Используемый исходящий тег (должен существовать в разделе «Исходящие» или «Конечные точки») |
| `type: "logical"` | Комбинированные условия с `mode`, установленным на `and` / `or`. |

Несколько полей в одном правиле объединяются оператором AND (например, `network` + `port`), поэтому нет
Требуется обертка `logical`. Используйте `type: "logical"` только для комбинаций ИЛИ/НЕ. `rule_set`
должен быть помещен внутри подправил `rules`, а не рядом с `rules`:

```jsonc
"rules": [
  { "domain_suffix": ["gstatic.com", "googleapis.com"], "outbound": "direct" },
  { "domain_keyword": ["ip.sb", "yandex.com"], "outbound": "warp" },
  { "rule_set": ["geosite-openai", "geosite-google"], "outbound": "warp" },
  { "rule_set": ["geoip-cn"], "outbound": "warp" },
  { "network": "tcp", "port": 443,
    "rule_set": ["geosite-google"], "outbound": "warp" },
  { "type": "logical", "mode": "or",
    "rules": [
      { "rule_set": ["geosite-google"] },
      { "rule_set": ["geosite-openai"] }
    ],
    "outbound": "warp" }
]
```

#### 6.6.3 Миграция правил xray

| xray | sing-box |
|------|----------|
| Голая строка (включая пустые значения в `domain`; совпадение подстроки) | `"domain_keyword": ["ip.sb"]` |
| `"domain": ["a.com"]` | `"domain_keyword": ["a.com"]`; используйте `"domain_suffix": ["a.com"]` для реального соответствия суффикса или `"domain": ["a.com"]` для точного совпадения |
| `"domain:clstorage.net"` | `"domain_suffix": ["clstorage.net"]` |
| `"full:a.com"` | `"domain": ["a.com"]` |
| `"regexp:..."` | `"domain_regex": ["..."]` |
| `"ip": ["geoip:cn"]` | `"rule_set": ["geoip-cn"]` |
| `"domain": ["geosite:cn"]` | `"rule_set": ["geosite-cn"]` |
| `"outboundTag": "direct"` | `"outbound": "direct"` |

Примечания:

- **Теги не являются общими для нескольких ядер**: исходящий тег xray нельзя использовать в правиле sing-box;
 используйте тег, который действительно существует в sing-box «Исходящие» или «Конечные точки».
- Неправильный тег исходящей или конечной точки сообщает `outbound not found`; сообщает неправильный набор правил
 `rule-set not found`.
- Сначала поставьте правила прямых/разрешенных списков; как только правило совпадает, последующие правила больше не применяются.

## 7. Управление прокси

Управление прокси-сервером настраивает обратный прокси-сервер Caddy или Nginx.

### 7.1 Типы прокси

- **Caddy**: автоматические HTTPS, HTTP/1.1 и HTTP/2 (HTTP/3 / QUIC отключены, чтобы избежать конфликта UDP 443 с маршрутизацией уровня 4)
- **Nginx**: высокая производительность, гибкая конфигурация.

### 7.2 Конфигурация сайта

1. Откройте «Управление прокси»;
2. Выберите тип прокси (Caddy/Nginx);
3. Добавить сайт:
   - Домен
   - вверх по течению
   - Местный порт
4. Сохранить.

### 7.3 Поля

- **восходящий**: внутренний адрес, например. `127.0.0.1:8082`
- **local_port**: локальный порт прослушивания, например. `8443`
- **portal_forward**: правило переадресации портала.
- **subscription_forward**: правило переадресации подписки.
- **Маршрутизация SNI**: когда входящий трафик использует TLS / REALITY и клиенты всегда подключаются по номеру 443, панель получает
 443 правила маршрутизации TCP из ClientHello SNI (оба xray `streamSettings` и sing-box `tls.reality`);
 передний прокси-сервер пересылает только TCP, а TLS все еще завершается внутри ядра

|-----|---------|
| Предпочтительные домены Direct и CF | Входные прямые домены/IP-адреса и предпочтительные домены Cloudflare, используемые при перезаписи адресов доступа в подписках и внешних узлах. |
| Пул IP-адресов CF | Предпочитаемые IP-источники, порты и настройки зондов, используемые «Доменом доступа». |
| Глобальные правила WAF | Источники правил и файлы правил для обратного прокси-сервера WAF, отправленные на узлы. |
| Файлы правил | Загрузка, синхронизация по расписанию и передача файлов правил (`.srs` / `.json` / `.dat`) |
| Внешние узлы | Импортировать внешние узлы из v2ray URI/Base64/подписки URL (см. 16.3) |

### 8.1 Предпочтительные домены Direct и CF

- **Прямой доступ**: входной домен или IP-адрес, порт 443 по умолчанию; привязать узлы или оставить пустыми для глобальных;
- **Предпочитаемые домены CF**: предпочтительный домен Cloudflare плюс порт с проверкой подключения;
- Оба подают кандидатов в «домен доступа», используемых подписками и перезаписью внешних узлов (см. 16.3).

- **Дрейф ввода (основной/резервный)**: прямой ввод может связать канал DNS и имя записи; после аварийного переключения или обратного переключения панель указывает на запись A на общедоступный IP-адрес текущего основного устройства (внутренний IP-адрес, если он пуст). Принимаются только провайдеры с реализованной функцией записи DNS (`cloudflare` проверено; alidns / DNSPod / GoDaddy / Namecheap / Route53 / Google / Huawei Cloud реализовано, но не проверено). Распространение Cloudflare измерено примерно за 2–2,5 минуты, при этом для TTL установлено значение 60; оставьте оранжевое облако выключенным для записей TCP/REALITY.

### 8.2 Пул IP-адресов CF

- Поддерживать предпочтительные источники IP (включая источники в стиле `bestproxy`), интервал выборки и порты;
- «Настройки зонда» управляют интервалом зондирования, порогом задержки и узлом входа зонда; местное зондирование
 фильтрует только явно недоступные IP-адреса, а выбор узла входа имитирует линию этого узла;
- The “dialer” may be automatic (installed cores), `singbox`, `xray` or `mihomo`; ядра, которых нет
 установленных не указаны. Зондирование выполняется как временный процесс, который завершается по завершении и никогда не считывает и не
 записывает собственную конфигурацию ядра;
- Когда «Домен доступа» использует пул IP-адресов CF без конкретного значения, одна запись (с его портом)
 выбрано случайно.

### 8.3 Глобальные правила WAF

- Настройте источник правил WAF URL и файлы правил для синхронизации;
- После синхронизации они передаются на узлы и загружаются прокси узла (Nginx/Caddy);
- С этого URL скачивается файл с полным URL; otherwise “source URL + /file name” is used;
- «Кэш совпадений» (`match_cache` / `config_match_cache`) включен по умолчанию: ограничение на уровне всего процесса.
 кэширование горячих результатов сопоставления правил уменьшает количество обходов правил для каждого запроса. Он глобальный, только без
 переопределение для каждого домена; временно отключите его для сравнения A/B при расследовании ложных срабатываний
 (отключение означает полную оценку правил при каждом запросе и более высокую загрузку ЦП).

автоматически. Чтобы использовать их при маршрутизации, укажите их в разделе «Центр протоколов → sing-box → Маршрутизация».

## 9. Центр подписки

Центр подписок упаковывает узлы в готовые для клиента подписки: определяет **форматы** подписки (что излучать, какие правила, какие планы могут их видеть), затем **конечные точки** подписки (общедоступный домен/путь), а затем раздает ссылки.

### 9.1 Форматы подписки

«Центр подписки» → «Форматы подписки»; одна строка на вывод клиента:

| Поле | Описание |
|---|---|
| Имя | Уникальный; `?config=<name>` соответствует ему, и это отображается в диалоговом окне клиента. |
| Тип клиента | clash/shadowrocket/singbox/v2ray — отображать только группировку |
| Выходной формат | `mihomo_yaml` (Clash/Mihomo), `singbox_json`, `xray_json`, `base64_uri`, `raw_uri` |
| Тип контента/расширение | Заголовок ответа и имя файла |
| Платформа | win/mac/android/ios/универсальный; соответствует `?platform=`, пусто = универсальное |
| Связанные планы | Пусто = доступно для каждого плана; в противном случае его смогут использовать только эти планы |
| Правила | Правила маршрутизации для каждого формата (структурный редактор для Mihomo, необработанный JSON для каждого правила для sing-box/Xray). **Правила не преобразуются между форматами** |

Примечания:

- Для одного и того же формата вывода может существовать несколько конфигураций (например, `out`, `home`); выберите один с `config=` по ссылке;
- Без `config` порядок следующий: «конфигурация, привязанная к подписке → совпадение `platform` → по умолчанию»;
- Шаблон sing-box может содержать собственный `route.rule_set` для клиентов, обычно как `remote`, поэтому
 клиент загружает его; локальные файлы, отправленные на `rules/` узла в разделе «Файлы правил», доступны только
 к ядру этого узла, а не к клиентским подпискам;
- При создании шаблонов sing-box/Xray панель удаляет висящие ссылки (`final`, `dns.final`,
 `default_domain_resolver`, `download_detour`, локальный `rule_set`, неверные определения `rule_set`, пусто
 `balancer` и т. д.), чтобы клиент не вылетал при запуске с ФАТАЛЬНОЙ ошибкой;
- Исходящие псевдонимы в правилах разрешаются по реальным тегам (`REJECT` / `blocked` → `block`, `DIRECT` →
 `direct`, регистронезависимо); неразрешимые исходящие вызовы возвращаются к исходящим по умолчанию и правилу
 сохраняет свою позицию;
- Всегда генерируется группа с `tag = proxy`: `selector` для sing-box и балансировщик `random` для
 Xray, а `outbound: proxy` в правилах переписаны на соответствующие `balancerTag`. Редактор правил загружается
 исходящие кандидаты динамически из «групп прокси + пользовательские исходящие», а теги, введенные вручную,
 все еще проверено;
- Конфиги sing-box/Xray необходимо создавать отдельно; если они не существуют, они не отображаются в ссылках клиентов (см. 10.3).

- Редактор структурированных правил Mihomo поддерживает логические правила `AND`/`OR`/`NOT`/`SUB-RULE`: записывайте условие как `((NETWORK,UDP),(DST-PORT,3478/19302))`; для `SUB-RULE` третий столбец — это имя группы подправил. Условия должны быть заключены в круглые скобки;
- Типы правил соответствуют последней версии mihomo: доступны `IP-SUFFIX`, `SRC-IP-CIDR/SRC-IP-SUFFIX/SRC-IP-ASN/SRC-GEOIP`, `IN-PORT/IN-TYPE/IN-USER/IN-NAME/REMATCH-NAME`, `PROCESS-NAME-WILDCARD/REGEX`, `PROCESS-PATH-WILDCARD/REGEX`, `UID`, `DSCP`;
- `SUB-RULE` ссылается на блок `sub-rules:` конфига mihomo; панель еще не редактирует этот блок, поэтому сначала определите его с помощью импорта YAML или общего config_json.

### 9.2 Конечные точки подписки

«Центр подписки» → «Конечные точки подписки»; одна строка на публичный адрес:

| Поле | Описание |
|---|---|
| Домен | Домен общедоступной подписки |
| Путь | Префикс под доменом, по умолчанию `/` |
| Включено | Отключенные конечные точки игнорируются при создании ссылок. |
| Описание | Произвольное текстовое примечание |

- **Поддерживается несколько строк (несколько доменов)**; если несколько из них включены, домен провайдера следует за доменом, используемым текущим запросом (см. 9.4);
- Выделенный порт подписки служит в корне (`/<token>`, нет `/sub`); при совместном использовании порта панели это `/sub/<token>`;
- Обратные прокси должны пересылать `X-Forwarded-Proto`/`X-Forwarded-Host`, в противном случае используется первая включенная конечная точка. Сгенерированные панелью шаблоны сайтов Caddy/Nginx включают оба заголовка; конфигурации прокси, поддерживаемые вручную, требуют их добавления вручную.

### 9.3 Ссылки на подписку

Базовая форма: `https://<sub-domain>/<token>` (порт панели: `https://<panel-domain>/sub/<token>`)

| Параметр | Описание |
|---|---|
| `format` | Выходной формат; псевдонимы: `clash` → mihomo_yaml, `singbox`/`sing-box` → songbox_json, `xray` → xray_json, `raw` → raw_uri, `base64`/`v2ray` → base64_uri |
| `config` | Применить формат подписки по имени; должно соответствовать `format`, в противном случае игнорируется |
| `platform` | Сопоставьте конфигурацию по платформе (если `config` опущен) |
| `providers` | `1` / `true`: Clash Режим провайдера (`proxy-providers` + `use`); встроенные узлы по умолчанию |

Примеры:

```bash
# Clash dynamic subscription (config template + providers)
https://sub.example.com/<token>?format=clash&config=out&providers=1

# sing-box / Xray (only meaningful when such a config exists)
https://sub.example.com/<token>?format=singbox_json&config=sing-box-home
https://sub.example.com/<token>?format=xray_json&config=xray-home

# generic clients / plain text
https://sub.example.com/<token>?format=base64_uri
https://sub.example.com/<token>?format=raw_uri
```

### 9.4 Мультидоменный режим и режим провайдера

При использовании `providers=1` каждый вход `proxy-providers` указывает обратно на конечную точку подписки. Выбор домена:

1. **Домен, использованный в этом запросе** (первое значение `X-Forwarded-Host`, порт удален, иначе `Host`), если он соответствует **включенной** конечной точке;
2. В противном случае включенная конечная точка с **самым низким идентификатором**;
3. Путь идет от этой конечной точки: `https://<domain><path>/<token>?format=mihomo_proxies_yaml...`.

Таким образом, для изменения домена не требуется смена панели: клиенты, получающие данные через новый домен, получают новый домен внутри провайдеров, а старый домен, оставленный включенным, больше не жестко запрограммирован. Если клиент закешировал старого провайдера URL, обновите подписку (или очистите кеш провайдера/перезапустите клиент).

Дополнительные примечания:

- `proxy-providers` внутри общего формата (`config_json`) игнорируется (во избежание утечки данных между планами); поставщики поступают из групп узлов плана и внешних источников;
- Пути к кэшу внутреннего и внешнего поставщика всегда извлекаются из «параметров по умолчанию внутреннего поставщика → шаблона пути к кэшу» (по умолчанию `./providers/{key}.yaml`); внешние источники не могут устанавливать свои собственные;
- Устаревший зарезервированный поставщик `subscription-nodes` больше не создается: группы, использующие «все узлы», расширяются до конкретных поставщиков или встроенных узлов, если в плане их нет.

1. Открыть «Управление клиентами»;
2. Нажмите «Добавить клиента»;

   - Пароль
   - План
   - Квота трафика

- **Возобновить**: восстановить заблокированного клиента
- **Сбросить трафик**: сбросить использованный трафик.
- **Сбросить пароль**: сбросить пароль клиента.

- **Обновление/понижение**: измените план.
- **Удалить**: удалить клиента.

### 10.3 Подробности подписки

Управление клиентами → графа «Подписка» → «Подробности». В диалоговом окне перечислены ссылки для каждого формата, доступного в плане клиента:

- **Clash / Mihomo**: две строки — встроенные узлы и `providers=1` (прокси-провайдеры), оба несут `config=<name>`;
- **Sing-box / Xray**: отображается только в том случае, если конфигурация этого формата существует и видна в плане; ссылки содержат `config=<name>`;
- **Base64 URI / Raw URI**: отображается всегда (без `config`);
- Каждая строка имеет собственную кнопку копирования; щелчок по строке переключает QR-код ниже в этот формат.

Таким образом, если используется только конфигурация Clash, в диалоговом окне отображается Clash + Base64 + Raw; Ссылки sing-box/Xray появляются только после создания их конфигов.

В том же диалоговом окне также отображается использование трафика, история заказов и история транзакций.

## 12. Управление пополнением

Управление пополнениями управляет сайтами пополнения счета, заказами и картами пополнения счета.

> **Интеграция платежей**
>
> Панель **не интегрируется напрямую с платежными учреждениями** (Alipay, WeChat Pay, Stripe, банки и т. д.). Он подключается только к **промежуточной платежной платформе**, которая, в свою очередь, интегрируется с соответствующим платежным учреждением, обрабатывает контракты, эквайринг и расчеты, а также сообщает о результатах платежа через обратный вызов [charge API](api/charge-callback.md).
>
> Промежуточная платежная платформа **не является частью этого проекта; операторы должны разработать ее самостоятельно (или использовать собственную систему)**. После развертывания зарегистрируйте его в разделе «Сайты пополнения счета» и завершите проверку домена, чтобы использовать его в качестве точки входа для пополнения счета; сайт пополнения счета здесь — это та самая промежуточная платформа, а не само платежное учреждение. Требования к платежам, комиссии, расчеты и соблюдение требований согласовываются и несут оператор, платежное учреждение и промежуточная платформа.

### 12.1 Места пополнения счета

1. Откройте «Управление пополнениями» → «Площадки пополнения»;
2. Добавить сайт:
   - Название сайта
   - Способы оплаты, поддерживаемые этой промежуточной платформой (Alipay, WeChat, USDT, Stripe и т. д., предоставляемые посредством интеграции с платежными учреждениями)
   - Валюта
   - Курс обмена
3. Сохранить;
4. Подтвердите сайт (файл HTTP или проверка DNS).

### 12.2 Заказы на пополнение счета

- Просмотреть все заказы на пополнение счета
- Фильтровать по статусу (ожидание, оплачено, не удалось, срок действия истек, возмещено)
- Посмотреть детали заказа
- Возврат средств администратору

## 25. Расширения операций

«Расширения операций» (`/client-ext`) настраивают реферальный маркетинг, комиссию и снятие средств;
«Юридические документы» (`/legal-documents`) поддерживают соглашения на стороне портала.

- **Просмотр отзыва**: фильтрация по ожидающим/утвержденным/отклоненным; добавьте примечание к обработке и запишите способ выплаты и адрес кошелька
- **Реферальные записи**: приглашающий, приглашенный, размер комиссии и статус комиссии.

### 25.2 Юридические документы

- Поддерживать «Политику конфиденциальности» и «Условия обслуживания» отдельно, по одному документу Markdown для каждой локали с предварительным просмотром в реальном времени;

## 26. Часто задаваемые вопросы

### 26.1 Панель не запускается

- Проверьте, используется ли порт уже
- Убедитесь, что `.env` действителен.
- Проверьте логи: `journalctl -u corefusion -f`; без systemd, `tail -f <install-dir>/data/logs/panel.log`

### 26.2 Узел не в сети

- Убедитесь, что агент запущен: `systemctl status corefusion-agent`.
- Проверьте подключение к сети
- Проверьте правила брандмауэра (порт `18443`)

### 26.3 Выдача сертификата не удалась

- Проверьте разрешение DNS
- Убедитесь, что порт 80 доступен.
- Проверьте конфигурацию провайдера DNS.
- Проверьте журналы сертификатов

### 26.4 Подписка не работает

- Проверьте ссылку на подписку
- Убедитесь, что узел находится в сети
- Убедитесь, что основной процесс запущен
- Проверьте правила брандмауэра

### 26.5 Не удалось выполнить обратный вызов пополнения счета

- Проверьте обратный вызов URL
- Убедитесь, что ключ сайта соответствует
- Проверьте список разрешенных IP-адресов
- Проверьте журналы заказов

### 26.6 Страница портала недоступна

- Убедитесь, что порт портала открыт
- Проверьте конфигурацию пути портала
- **Важно**: убедитесь, что обратный прокси-сервер перенаправляет домен портала на **порт механизма портала**, а не на порт основной панели — при пересылке на неправильный порт вместо портала отображается пустая страница или панель. Проверьте `upstream`/`local_port` в записи прокси-сайта.
- Откройте `http://<portal-domain>:<portal-port>` напрямую, чтобы проверить сам механизм портала.
- Проверьте конфигурацию обратного прокси
- Проверьте логи портала

## Приложение

### А. Порты по умолчанию

| Порт | Цель |
|------|---------|
| Назначается мастером настройки (по умолчанию произвольный свободный порт) | Админ панель (изменяемая) |
| 18443 | Агент gRPC (изменяемый) |
| 0 (отключено по умолчанию) | Выделенный порт механизма подписки (пустой или `0` использует основной порт) |
| 0 (отключено по умолчанию) | Выделенный порт механизма портала (пустой или `0` использует основной порт) |
| 80 / 443 | Обратный прокси (Caddy/Nginx) HTTP/HTTPS |

### Б. Пути по умолчанию

| Путь | Цель |
|------|---------|
| `/` | Панель администратора (портал также находится по адресу `/`, если не настроен специальный механизм портала) |
| `/sub/:token` | Получение подписки (если выделенный порт подписки не настроен) |
| `/p` | Страница портала (если выделенный порт портала не настроен) |
| `/:token` | Получение подписки (с выделенным портом подписки, без префикса `/sub`) |

### C. Инструмент командной строки

Бинарный файл панели поддерживает следующие подкоманды (без аргументов запускает сервер):

```bash
# Start the panel (same as ./corefusion server)
./corefusion

# Run database migrations
./corefusion migrate

# Non-interactive init / reset init state (see 3.4, 3.5)
./corefusion init --help
./corefusion reset-init

# Offline administration (when you cannot sign in)
./corefusion admin reset-password -u admin -p 'new-password'
./corefusion admin 2fa reset -u admin
./corefusion admin list

# Version / help
./corefusion version
./corefusion help
```

> С systemd используйте `systemctl restart corefusion` и `journalctl -u corefusion -f`; без
> systemd (контейнеры и т.п.), остановите старый процесс и запустите его снова с помощью `nohup`, логи будут сохранены.
> в `data/logs/panel.log`.

## Изменения v0.13.0-rc.1

- **Онлайн-обновление панели**: «Системные настройки → Обновление панели» — выбор версии
  (метка `pre` = предрелиз), обновление, история задач и откат к предыдущему бинарнику.
- **Онлайн-обновление Agent**: в карточке узла «Обновление Agent» — из локального бинарника
  панели или из GitHub Releases; узлы, обновлённые со старых версий, при первом подключении
  автоматически получают `update.public_key` (0600) и далее проверяют подпись ed25519.
- **Синхронизация WAF**: время последней синхронизации хранится в
  `waf.github_source.last_sync`, перезапуск не сбрасывает таймер; `0 3 * * *` выполняется
  в 03:00 по часовому поясу `panel.timezone` (по умолчанию Asia/Shanghai); пропущенные
  окна догоняются примерно через 15 секунд после старта.
- **Белый список WAF**: для домена панели автоматически ведётся `whiteurl.rule`; проверки
  URL/параметров/POST пропускаются только для админ-API, поэтому сохранение платёжного
  сайта с адресом вида `http://127.0.0.1:18081` больше не блокируется правилом SSRF.
- **Политика квоты**: накопление при продлении / очистка при истечении / сброс при
  продлении (вариант может наследовать тариф); при «ежемесячно» панель ежечасно проверяет
  и обнуляет использование.
- **Платёжные сайты**: включение/выключение больше не меняет ключи и способы оплаты;
  заказы пополнения фильтруются по типу и выгружаются в CSV.
- **Портал**: кнопка «Пополнить» поддерживает онлайн-оплату через включённый платёжный
