## 1. System overview

CoreFusion is a multi-protocol proxy management panel supporting VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC and more, with node management, subscription delivery, customer management, billing, certificates and chained proxies.

### 1.1 Core features

| Module | Description |
|--------|-------------|
| Multi-protocol | VLESS, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, WireGuard, etc. |
| Multi-core | Xray-core and sing-box (Hysteria2/TUIC and other QUIC protocols run on sing-box) |
| Multi-node | Five node types: standalone, mirror, active/standby, chained entry, chained exit |
| Subscription delivery | Multiple subscription formats, endpoints and format management |
| Billing | Plan templates, recharge cards, balance, orders, reseller commission |
| Certificates | Let's Encrypt issuance, DNS-01/HTTP-01 validation, certificate distribution |
| Chained proxy | Multi-exit load balancing, external node registration, chained routing |
| Traffic quotas | Per-node monthly traffic monitoring, auto-suspend, reset logs |
| Portal | Visual portal editor, multilingual, custom templates |
| Notifications | Email and Telegram, templates and broadcasts |

### 1.2 Architecture

- **Backend**: Go, gRPC
- **Frontend**: Vue 3 + Element Plus
- **Database**: SQLite (default) / MySQL / PostgreSQL
- **Proxy**: Caddy / Nginx reverse proxy
- **Panel port**: assigned by the setup wizard (random free port by default; 8080 is a common choice)
- **Agent gRPC port**: 18443 by default

## 2. Installation

### 2.1 Supported environments

| Item | Support |
|------|---------|
| Distributions | Debian / Ubuntu, RHEL / CentOS / Rocky / AlmaLinux / Fedora, Alpine, Arch, openSUSE |
| CPU architectures | Official binaries: `amd64`, `arm64`; source builds also support `armv7`, `armv6`, `386`, `ppc64le`, `s390x`, `riscv64`, `loong64` |
| Service manager | systemd (recommended); falls back to `nohup` in containers or other environments without systemd |
| Memory / disk | ≥ 1 GB / ≥ 10 GB (database, certificates, logs and core binaries live in the data directory) |
| Panel port | chosen in the setup wizard (random free port by default; `8080` and similar are fine) |
| Agent gRPC | `18443` by default |

Runtime external commands are installed automatically by the installer (`scripts/install.sh` and the Agent install script generated by the panel; skip with `--no-deps` / `CF_SKIP_DEPS=1`):

| Purpose | Package |
|---------|---------|
| Firewall / rate limit / concurrency marking | `nftables` (`nft`) |
| Traffic shaping, links and sockets | `iproute2` (`tc` / `ip` / `ss`) |
| Fallback when nft is unavailable | `iptables` (`iptables-nft` on EL8+, `iptables` on EL7) |
| Connection tracking | `conntrack-tools` (`conntrack`) |
| Load `nf_conntrack` / `ifb` | `kmod` (`modprobe` / `lsmod`) |
| Process detection and cleanup | `procps` (`pgrep` / `pkill`) |
| Port checks / DH parameters | `lsof` / `openssl` |
| Proxy user creation | `shadow-utils` (Debian `passwd`, Alpine/Arch `shadow`) |
| Downloads and archives | `curl` / `ca-certificates` / `tar` / `gzip` / `xz` |

> Missing `nft` / `tc` only affects rate limiting and firewall features; the panel still starts.
> Run `--cpu-info` first to see how the environment is detected and which packages are missing.

### 2.2 One-line installation (recommended)

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh -o install.sh
sudo bash install.sh
```

Or pipe it directly (no interaction, no extra flags):

```bash
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash
```

The script will:

1. Detect the distribution, CPU architecture and libc, then install base packages and runtime dependencies;
2. Download `corefusion-linux-<arch>` from GitHub Releases and verify it with the matching `.sha256`;
3. Install to `/opt/corefusion` and create `data/{sqlite,certs,logs,runtime}`;
4. Write only a placeholder `.env` with `SAFE_PATHS=data` — no database config — so the first start enters the setup wizard (the full `.env` is generated by the wizard);
5. Install and start a systemd service (or run under `nohup` when systemd is unavailable);
6. Wait until ready, then print the setup URL, token and directory paths.

Example output:

```text
==================================================================
 CoreFusion installation complete
------------------------------------------------------------------
 Install dir : /opt/corefusion
 Data dir    : /opt/corefusion/data
 Binary      : /opt/corefusion/corefusion
 Logs        : journalctl -u corefusion -f
------------------------------------------------------------------
 Setup wizard : http://<server-ip>:<random-port>/init?init_token=<token>
 Setup token  : <token>
 Valid for    : 2 hours (see startup log)
 Note         : the token is shown once; after setup this port closes and the panel switches to its normal port.
==================================================================
```

If the panel only listens on `127.0.0.1` (for example behind a reverse proxy), the script prints an SSH tunnel command instead of an unreachable URL.

> Lost the token? Read the startup log again: `journalctl -u corefusion -n 50 --no-pager`
> (without systemd: `tail -n 50 /opt/corefusion/data/logs/panel.log`).

### 2.2.1 Multilingual output

The installer includes four UI languages: Simplified Chinese, English, Persian (فارسی), and Russian (Русский). It auto-detects the system `LANG`, or you can choose explicitly:

```bash
# English
sudo bash install.sh --lang en

# Persian via environment variable
sudo CF_LANG=fa bash install.sh

# Pass options through a pipe
curl -fsSL https://raw.githubusercontent.com/qist/corefusion/main/scripts/install.sh | sudo bash -s -- --lang ru
```

Supported values: `zh` / `en` / `fa` / `ru`; `--lang=ru` is also accepted. An unsupported explicit value fails with the list of available languages.

### 2.3 Version pinning / mirrors / offline install

```bash
# Pin a version
sudo bash install.sh --version v0.13.0-beta.82

# GitHub download mirror (used as a URL prefix)
sudo bash install.sh --mirror https://ghproxy.net --version latest

# Use a local binary (offline / intranet / pre-built)
sudo bash install.sh --local ./dist/corefusion-linux-arm64

# Explicit target architecture
sudo bash install.sh --arch arm64 --local ./corefusion-linux-arm64
```

> Without `--version`, the script uses the newest entry in the GitHub Releases list.
> Most releases are pre-releases, so the `/releases/latest` endpoint is not used.
>
> Official releases only provide `amd64` / `arm64`; use `--source` or a cross-compiled binary with `--local` for other architectures.

### 2.4 Building from source

```bash
sudo bash install.sh --source --version v0.13.0-beta.82
```

`--source` clones the repository (or uses the existing checkout when the script is inside it) and runs `make panel`. Toolchain versions are chosen per environment:

| Dependency | Selection |
|------------|-----------|
| Go | Read from `toolchain` / `go` in `go.mod` (currently **Go 1.27+**); if the system version is too old, the matching toolchain is downloaded to `<install-dir>/.toolchain` |
| Node | **Node 22 LTS** by default (Vite requires ≥ 18); a matching official build is downloaded when needed |
| Node (glibc < 2.28) | Uses the `unofficial-builds` glibc-217 build (e.g. CentOS 7) |
| Node (Alpine / musl) | Uses the distribution `nodejs` / `npm` |

Overrides:

```bash
# Force Go / Node versions
sudo CF_GO_VERSION=1.27.5 CF_NODE_MAJOR=22 bash install.sh --source

# Go toolchain mirror (default https://go.dev/dl)
sudo CF_GO_MIRROR=https://golang.google.cn/dl bash install.sh --source
```

Manual build (development / debugging):

```bash
git clone https://github.com/qist/corefusion.git
cd corefusion

# Frontend + panel for the current architecture; the frontend is embedded via go:embed
make panel

# Cross-compile
make panel-linux-amd64
make panel-linux-arm64
```

> `go build ./...` does not produce a binary. Build the panel with
> `go build -o corefusion ./cmd/corefusion/` or `make panel`.

### 2.5 Installer flags

| Flag | Description |
|------|-------------|
| `-d, --dir <PATH>` | Install directory, default `/opt/corefusion` |
| `-v, --version <TAG>` | Panel version, e.g. `v0.13.0-beta.82`; default `latest` |
| `--binary` | Use the GitHub Release binary (default) |
| `--source` | Build from source and prepare matching Go / Node |
| `--local <FILE>` | Use a local binary (offline install) |
| `--arch <ARCH>` | Target architecture: `amd64` / `arm64` / `armv7` / `armv6` / `386` / `ppc64le` / `s390x` / `riscv64` / `loong64` |
| `--mirror <URL>` | GitHub download prefix, e.g. `https://ghproxy.net` |
| `--repo <URL>` | Source repository, default `https://github.com/qist/corefusion.git` |
| `--ref <REF>` | Source branch / tag; defaults to `--version`, otherwise `main` |
| `--no-deps` | Skip system dependency installation |
| `--no-start` | Install and write the service file without starting |
| `--cpu-info` | Print environment detection and missing dependencies, then exit |
| `--lang <LANG>` | Output language: `zh` / `en` / `fa` / `ru` (default: system `LANG`) |
| `--uninstall` | Stop the service and remove the program (keeps data and `.env`) |
| `--purge` | With `--uninstall`, also remove the data directory and `.env` |

> Official releases only ship `amd64` / `arm64` binaries. Other architectures require `--source`,
> otherwise the download returns 404.

Related environment variables:

| Variable | Purpose |
|----------|---------|
| `CF_GO_VERSION` | Override the Go version required for source builds |
| `CF_NODE_MAJOR` | Override the Node major version (default 22) |
| `CF_GO_MIRROR` | Go toolchain download mirror |
| `CF_SKIP_DEPS` | Set to `1` in the Agent install script to skip dependency installation |
| `CF_LANG` | Override installer output language (same as `--lang`) |

### 2.6 Directory layout

```text
/opt/corefusion/
├── corefusion                 # panel binary
├── corefusion.bak             # previous version (when upgrading)
├── .env                       # environment file (0600, generated by the setup wizard)
├── .env.secret                # encryption key file (0600, generated on first start)
├── .toolchain/                # Go / Node downloaded for source builds
└── data/                      # data directory (SAFE_PATHS)
    ├── sqlite/app.db          # default SQLite database
    ├── certs/                 # certificates and keys
    ├── logs/                  # runtime logs (without systemd)
    ├── runtime/               # core runtime config and state
    ├── binaries/              # downloaded xray / sing-box cores
    └── proxy/                 # proxy (Caddy/Nginx) sites and config
```

> The installer only creates `sqlite/`, `certs/`, `logs/` and `runtime/`; `binaries/`, `proxy/`, `rules/` and others are created by the panel or when cores are installed.
> The data directory comes from `SAFE_PATHS` in `.env` and may be an absolute path. Changing the install directory does not move existing data.

### 2.7 Service management

systemd (most distributions):

```bash
systemctl status corefusion --no-pager
systemctl restart corefusion
systemctl stop corefusion
journalctl -u corefusion -f          # follow logs
journalctl -u corefusion -n 100      # last 100 lines
```

Without systemd (containers, etc.):

```bash
cd /opt/corefusion && ./corefusion            # foreground (debugging)
cd /opt/corefusion && setsid nohup ./corefusion >> data/logs/panel.log 2>&1 &
tail -f data/logs/panel.log
```

> Without systemd the process does not start on boot; restart it manually after a reboot (or rerun the installer).

### 2.8 Upgrade and uninstall

Upgrade (keeps data and config):

```bash
sudo bash install.sh --version <new-version>
```

The script stops the service, backs up the old binary as `corefusion.bak`, replaces it and restarts. Existing `.env` and `data/` are left untouched.

Uninstall:

```bash
# Remove the program only; keep data and .env
sudo bash install.sh --uninstall

# Also remove the data directory and .env (irreversible)
sudo bash install.sh --uninstall --purge
```

### 2.9 Environment file (.env)

The complete `.env` is **generated by the setup wizard** when the configuration is saved (database DSN, data directory, secrets, ports, domains).

On a fresh install the installer writes only this placeholder, so the panel does not mistake the existing `data/` for an initialized installation and skip the wizard:

```env
SAFE_PATHS=data
```

> When a complete config (`.env` with `CF_DB_DSN`) already exists, the installer never overwrites it and the wizard does not appear again.
> Later manual edits to `.env` take effect after a restart.

#### Data directory

```env
SAFE_PATHS=data                       # relative to the install directory
# SAFE_PATHS=/srv/corefusion-data     # or an absolute path
```

#### Database

`CF_DB_DSN` is detected by prefix:

| Prefix | Database |
|--------|----------|
| unset or a bare path | SQLite (default) |
| `sqlite://` | SQLite (explicit) |
| `mysql://` | MySQL |
| `postgres://` / `postgresql://` | PostgreSQL |

`CF_DB_TYPE` is optional and overrides detection (`sqlite` / `mysql` / `postgres`).

> **Encrypted passwords**: MySQL/PostgreSQL DSNs written by the panel (setup wizard / database switch)
> are stored in `.env` as `enc:...` (AES-256-GCM, key `CF_SECRET_ENCRYPTION_KEY`).
> They are decrypted on read; plaintext DSNs written by hand still work.

**SQLite (default)**

```env
# Bare path (detected as SQLite)
CF_DB_DSN=data/sqlite/app.db

# Or explicit sqlite:// prefix
CF_DB_DSN=sqlite:///opt/corefusion/data/sqlite/app.db
```

**MySQL**

```env
# Format: mysql://user:password@tcp(host:port)/dbname?params
CF_DB_DSN=mysql://corefusion:password@tcp(127.0.0.1:3306)/corefusion?charset=utf8mb4&parseTime=True&loc=Local
```

**PostgreSQL**

```env
# Format: postgres://user:password@host:port/dbname?params
CF_DB_DSN=postgres://corefusion:password@127.0.0.1:5432/corefusion?sslmode=disable
```

#### Connection pool (optional, MySQL/PostgreSQL)

```env
CF_DB_MAX_OPEN_CONNS=100
CF_DB_MAX_IDLE_CONNS=10
```

#### Other common variables

| Variable | Description |
|----------|-------------|
| `JWT_SECRET` | Signing key for login tokens; generated on first start when missing |
| `CF_SECRET_ENCRYPTION_KEY` | Key for encrypting sensitive settings (AES-256-GCM); generated when missing |
| `CF_INITIAL_ADMIN_PASSWORD` | Initial admin password (optional; random and printed once by default) |
| `CF_NETWORK_TRAFFIC_ACCOUNTING` | Set to `0` to disable iptables-based traffic accounting (enabled by default) |
| `CF_NETWORK_TRAFFIC_TABLE` | iptables table used for traffic accounting, default `corefusion` |

> **The encryption key lives in `.env.secret`**: on first start `CF_SECRET_ENCRYPTION_KEY` is written to `.env.secret` (0600, same directory as `.env`) instead of `.env`; a legacy key in `.env` is migrated automatically. Back this file up separately — losing it makes every `enc:` value undecryptable.

> Trusted reverse proxies for resolving real client IPs are no longer configured via environment variables;
> they are stored as `panel.trusted_proxies` in **Settings → Network**.

> Both `.env` and `.env.secret` contain secrets; the panel tightens their permissions to `0600` on start. Never commit them.

### 2.10 Docker (optional, build your own image)

The repository does **not** ship a Dockerfile. If you containerize it, write your own image. Reference invocation:

```bash
docker run -d \
  --name corefusion \
  -p 8080:8080 \
  -p 18443:18443 \
  -v /opt/corefusion/data:/app/data \
  -v /opt/corefusion/.env:/app/.env \
  <your-image>
```

> Containers usually have no systemd and no `nft` privileges, so rate limiting / firewall features will not work.
> The working directory must match the base for relative `SAFE_PATHS`.

## 3. Initial configuration

On first start, if `.env` has no valid `CF_DB_DSN`, the panel does **not** serve the admin UI yet. It starts the
**setup wizard** on a random port in 18000–18999 with a one-time token, then restarts as the normal panel once saved.

### 3.1 Open the setup wizard

1. Copy the “setup wizard” URL from the installer output; or
2. Read the log on the server:

```bash
journalctl -u corefusion -n 50 --no-pager | grep -A2 'setup wizard'
```

```text
CoreFusion first start - setup wizard
  URL   : http://<ip>:<port>/init?init_token=<token>
  Token : <token>
  Valid : 2h0m0s
```

3. Open the URL in a browser (it already contains `init_token`, so no manual entry is needed).

> The wizard session expires after **2 hours** by default. If it expires or the panel restarts, obtain a new one.
> Do not share the token. Once setup completes, this port closes and only the normal panel port remains.

### 3.2 Wizard steps

The wizard has 8 steps. You can go back at any time; nothing is committed until the final save.

| Step | Content |
|------|---------|
| 1. Database | SQLite / MySQL / PostgreSQL |
| 2. Data directory | Written to `SAFE_PATHS` in `.env` |
| 3. Encryption keys | `JWT_SECRET` and `CF_SECRET_ENCRYPTION_KEY` |
| 4. Cores | Which proxy cores to install |
| 5. Proxy | None / Nginx / Caddy |
| 6. Sites and domains | Ports, web path, admin account, currency, timezone, domains |
| 7. HTTPS certificate | Disabled / upload / ACME |
| 8. Summary | Review, download `.env`, save and restart |

#### Step 1: Database

- **SQLite (local file, recommended)**: leave the path empty to use `<data-dir>/sqlite/app.db`.
- **MySQL / PostgreSQL**: host, port, user, password, database name; PostgreSQL also supports `disable` / `require` / `verify-full`.
- Click “Test connection” to validate. Saving also tests it. A missing database is created automatically (create it manually if the account lacks `CREATE`).
- The DSN (including the password) is encrypted before being written to `.env`.

#### Step 2: Data directory

Stores the database, certificates, logs, core binaries and more; this is `SAFE_PATHS` in `.env`. Defaults to `data`
(relative to the install directory); an absolute path is allowed. **Do not change it casually later**, or the panel
will not find the existing database and certificates.

#### Step 3: Encryption keys

- `JWT_SECRET`: signs login tokens.
- `CF_SECRET_ENCRYPTION_KEY`: encrypts sensitive settings (database password, DNS credentials, recharge cards, etc.).
- Both are generated randomly by default; use “Regenerate” to get new values. **Changing `CF_SECRET_ENCRYPTION_KEY` makes previously encrypted data unreadable** — back it up.

#### Step 4: Cores

Select the proxy cores to install:

- **Xray**: VLESS / VMess / Trojan / Shadowsocks, etc.;
- **sing-box**: carries Hysteria2 / TUIC and other QUIC protocols.

After save and restart the panel downloads and installs them automatically. Check versions and status under “Protocols”. You can also install them later.

#### Step 5: Proxy

- **None**: the panel serves clients directly (handle TLS yourself).
- **Nginx / Caddy**: the panel manages the reverse proxy and certificate hosting; pick one.

With a proxy selected, the panel usually listens only on `127.0.0.1` and the proxy serves the outside world.

#### Step 6: Sites and domains

| Field | Description |
|-------|-------------|
| Listen address | Derived automatically: proxy → `127.0.0.1`; no proxy with a certificate → `0.0.0.0`; otherwise → `127.0.0.1` |
| Panel port | Random free port by default; change it if you like (e.g. 8080) |
| Subscription port | Optional; `0` shares the panel port |
| Portal port | Optional; `0` shares the panel port |
| Web path | Admin UI path, default `/`; the API is always `/api/v1` |
| Admin username / password | Random by default; **the password is shown only once in the summary** — save it |
| Access mode | “Domain” or “IP” |
| Default currency / timezone | Default currency for recharge cards and balances; panel and proxy log timezone (e.g. `Asia/Shanghai`) |
| Add to reverse proxy | When a proxy and domains are set, add panel / subscription / portal domains to the proxy in one go |

Entering domains writes the corresponding settings (callback domain, subscription endpoint, share domain).

#### Step 7: HTTPS certificate

| Source | Description |
|--------|-------------|
| Disable HTTPS | Panel/portal/subscriptions are served over HTTP (insecure); with a reverse proxy you can add TLS on the proxy side later |
| Upload certificate | Paste certificate PEM and private key PEM (domain access mode only) |
| ACME | Issues the certificate when you submit this step; supports domain and IP certificates |

ACME options:

- **CA**: Let's Encrypt, Let's Encrypt (Staging), ZeroSSL, Google Public CA;
- **Target**: the configured domain, or the public IP (IP certificates are supported by Let's Encrypt only);
- **Challenge**: `HTTP-01` (requires port 80) or `DNS-01` (wildcards, no port 80; choose a DNS provider and enter credentials);
- **Key type / size**: ECC 256/384 or RSA 2048/3072/4096;
- **Google Public CA**: requires EAB; enter Key ID / HMAC manually or use a GCP service account.

> IP certificates auto-detect the host's public IPv4/IPv6. Behind a proxy, the detected address is the host's, not the proxy egress.
> Domain certificates can also be issued later under “Certificates”.

#### Step 8: Summary

Shows the database, data directory, cores, proxy, ports, admin account, domains and `.env` keys (secrets masked), and provides:

- **Download .env**: keep a copy of the configuration;
- **Access URLs**: final URLs for panel / subscription / portal; HTTP is marked as insecure.

Click “Save and restart” to write the database and `.env`; the panel restarts into normal service.

### 3.3 After setup

- The service restarts and the startup log prints the final listen address;
- Sign in with the admin account, access URL and web path from the summary;
- If the password is lost, reset it offline with `./corefusion admin reset-password`.

### 3.4 Non-interactive CLI setup

For automation or headless servers, write the config and mark setup complete directly:

```bash
cd /opt/corefusion
./corefusion init \
  --db-type sqlite \
  --data-dir /opt/corefusion/data \
  --admin-username admin \
  --admin-password 'change-me-strong-password' \
  --listen-port 8080 \
  --proxy-type caddy \
  --cores xray,singbox \
  --panel-domain panel.example.com \
  --tls-mode acme --tls-domain panel.example.com --tls-email you@example.com
```

Common flags:

| Flag | Description |
|------|-------------|
| `--db-type` / `--db-host` / `--db-port` / `--db-user` / `--db-password` / `--db-name` | Database settings |
| `--data-dir` | Data directory; defaults to `SAFE_PATHS` or `./data` |
| `--listen-port` / `--subscription-port` / `--portal-port` / `--web-path` | Ports and web path (random free port by default) |
| `--admin-username` / `--admin-password` | Admin account (random password printed once when omitted) |
| `--proxy-type` | `none` / `nginx` / `caddy` |
| `--cores` | Cores to install, comma separated: `xray,singbox` |
| `--panel-domain` / `--subscription-domain` / `--portal-domain` | Domains (written to settings and added to the reverse proxy) |
| `--tls-mode` | `none` / `self_signed` / `acme` |
| `--tls-domain` / `--tls-email` / `--tls-challenge` / `--tls-key-type` / `--tls-key-bits` | Certificate options (`--tls-challenge` defaults to `http-01`; `dns-01` needs `--tls-dns-channel` or `--tls-dns-provider`) |
| `--tls-ip-cert` | Issue a certificate for the detected public IP (Let's Encrypt only) |
| `--acme-provider` | `lets_encrypt` / `lets_encrypt_staging` / `zerossl` / `google` |
| `--currency` / `--timezone` | Default currency / timezone |

Full list: `./corefusion init --help`. Then start the service:

```bash
systemctl restart corefusion
```

### 3.5 Re-running the setup wizard

To start over (removes `.env` and the setup marks, **keeps data**):

```bash
cd /opt/corefusion
./corefusion reset-init      # type RESET to confirm
systemctl restart corefusion
```

Then use the new URL and token from the startup log.

> Re-initialization resets the admin account and web path. Business data in the old database remains, but you may need to recreate the login account.
>
> `reset-init` deletes the whole `.env` (including `SAFE_PATHS`). **If your data directory is a custom absolute path**, restore `SAFE_PATHS` before restarting, otherwise the panel looks in `./data`:
>
> ```bash
> printf 'SAFE_PATHS=/srv/corefusion-data\n' > /opt/corefusion/.env
> ```

### 3.6 Security after first sign-in

#### Change the initial password

1. Click the username in the top-right corner;
2. Choose “Change password”;
3. Enter the old and new passwords;
4. Click “Save”.

#### Enable dynamic-code login (2FA / TOTP)

> Once enabled, the account switches to **dynamic-code login**: the static password is no longer accepted; only the
> 6-digit code from your authenticator app (or a one-time recovery code) works. This **replaces** password login — it is
> not “password + code” two-step verification.

1. Click the username in the top-right corner;
2. Choose “Enable 2FA”;
3. Enter the current password (only to confirm this change);
4. Scan the QR code with an authenticator app (Google Authenticator / 1Password, etc.), or enter the key manually;
5. Enter the 6-digit code to finish enabling;
6. **Save the recovery codes immediately** (downloadable); each code works once.

Signing in afterwards:

- After entering the username, the password field becomes “6-digit code / recovery code” and the button becomes “Sign in with Code”;
- Enter the current code; **the static password can no longer be used**;
- Recovery codes are single-use; regenerate them under “Dynamic Code Login (2FA)” when they run out (this invalidates all old codes).

If the authenticator is lost and recovery codes are exhausted, disable 2FA offline on the server:

```bash
cd /opt/corefusion
./corefusion admin 2fa reset -u admin    # disables 2FA, clears the secret and recovery codes, revokes all sessions
```

> A sole super-admin with neither the authenticator nor recovery codes cannot recover through the web UI and must use the command above.

#### Register a Passkey (optional)

1. Click the username in the top-right corner;
2. Choose “Passkey management”;
3. Click “Register new Passkey”;
4. Complete the device prompt.

> **Note**: Passkeys require HTTPS or localhost, and the domain must be allow-listed.

### 6.6 sing-box routing and rule sets

In “Protocol center” → sing-box → “Routing” there are two parts: **Rule Sets** declare reusable
rule files, and **Rules** decide the match conditions and the outbound. Rules are evaluated from
top to bottom and the first match wins.

#### 6.6.1 Rule Sets

| Field | Description |
|-------|-------------|
| tag | Rule-set identifier referenced by Rules; must be unique |
| Type | `local` reads a file on the node; `remote` lets the core download it on `update_interval` |
| Format | `binary` for `.srs` (default); `source` for source-format `.json` |
| Path | `local` paths are relative to the node data directory; files in `data/rules/` use `rules/xxx.srs` |
| URL | Download address for `remote`; `download_detour` selects the outbound used for the download (usually `direct`) |

Local rule sets (recommended; download the files first under “Service resources → Rule files”):

```jsonc
"route": {
  "rule_set": [
    { "type": "local", "tag": "geosite-cn", "format": "binary", "path": "rules/geosite-cn.srs" },
    { "type": "local", "tag": "geoip-cn", "format": "binary", "path": "rules/geoip-cn.srs" }
  ]
}
```

> Downloading the file on the panel is not enough: a `local` rule set must first be pushed to the
> nodes (“Push to all nodes”) so the file exists in the node's `data/rules/`; otherwise the core
> fails to start because the file cannot be found.

Remote rule sets (the node must be able to reach the URL):

```jsonc
{ "type": "remote", "tag": "geosite-openai", "format": "binary",
  "url": "https://raw.githubusercontent.com/SagerNet/sing-geosite/rule-set/geosite-openai.srs",
  "download_detour": "direct", "update_interval": "1d" }
```

When you pick a local file the tag is derived from the file name (`rules/geosite-cn.srs` →
`geosite-cn`); for remote sets it comes from the end of the URL. The format is also filled in from
the extension (`.srs` → `binary`, `.json` → `source`). Derived values can be edited freely, and
values you already typed are never overwritten.

> `download_detour` has been deprecated since sing-box 1.14 and will be removed in 1.16; it still
> works in 1.15. New configurations should use top-level `http_clients` with
> `route.default_http_client` instead.

#### 6.6.2 Rules

| Field | Matches |
|-------|---------|
| `domain` | Exact domain |
| `domain_suffix` | Domain suffix, including subdomains |
| `domain_keyword` | Substring match |
| `domain_regex` | Regular expression |
| `ip_cidr` / `ip_is_private` | Destination IP |
| `source_ip_cidr` | Source IP |
| `port` / `port_range` | Destination port |
| `network` | `tcp` / `udp` |
| `rule_set` | Tags of the Rule Sets to use |
| `outbound` | Outbound tag to use (must exist under “Outbounds” or “Endpoints”) |
| `type: "logical"` | Combined conditions with `mode` set to `and` / `or` |

Multiple fields in one rule are combined with AND (for example `network` + `port`), so no
`logical` wrapper is needed. Use `type: "logical"` only for OR / NOT combinations. `rule_set`
must be placed inside the `rules` sub-rules, not next to `rules`:

```jsonc
"rules": [
  { "domain_suffix": ["gstatic.com", "googleapis.com"], "outbound": "direct" },
  { "domain_keyword": ["ip.sb", "yandex.com"], "outbound": "warp" },
  { "rule_set": ["geosite-openai", "geosite-google"], "outbound": "warp" },
  { "rule_set": ["geoip-cn"], "outbound": "warp" },
  { "network": "tcp", "port": 443,
    "rule_set": ["geosite-google"], "outbound": "warp" },
  { "type": "logical", "mode": "or",
    "rules": [
      { "rule_set": ["geosite-google"] },
      { "rule_set": ["geosite-openai"] }
    ],
    "outbound": "warp" }
]
```

#### 6.6.3 Migrating xray rules

| xray | sing-box |
|------|----------|
| Bare string (including bare values in `domain`; substring match) | `"domain_keyword": ["ip.sb"]` |
| `"domain": ["a.com"]` | `"domain_keyword": ["a.com"]`; use `"domain_suffix": ["a.com"]` for a real suffix match or `"domain": ["a.com"]` for an exact match |
| `"domain:clstorage.net"` | `"domain_suffix": ["clstorage.net"]` |
| `"full:a.com"` | `"domain": ["a.com"]` |
| `"regexp:..."` | `"domain_regex": ["..."]` |
| `"ip": ["geoip:cn"]` | `"rule_set": ["geoip-cn"]` |
| `"domain": ["geosite:cn"]` | `"rule_set": ["geosite-cn"]` |
| `"outboundTag": "direct"` | `"outbound": "direct"` |

Notes:

- **Tags are not shared between cores**: an xray outbound tag cannot be used in a sing-box rule;
  use a tag that really exists under sing-box “Outbounds” or “Endpoints”.
- A wrong outbound or endpoint tag reports `outbound not found`; a wrong rule-set tag reports
  `rule-set not found`.
- Put direct / allow-list rules first; once a rule matches, later rules no longer apply.

## 8. Routing resources

Routing resources collect the shared assets used by subscriptions and routing. The page has five tabs:

| Tab | Purpose |
|-----|---------|
| Direct & CF preferred domains | Ingress direct domains / IPs and Cloudflare preferred domains, used when rewriting access addresses in subscriptions and external nodes |
| CF IP pool | Preferred IP sources, ports and probe settings, consumed by “Access domain” |
| WAF global rules | Rule sources and rule files for the reverse-proxy WAF, pushed to nodes |
| Rule files | Download, scheduled sync and push of rule files (`.srs` / `.json` / `.dat`) |
| External nodes | Import external nodes from v2ray URI / Base64 / subscription URL (see 16.3) |

### 8.1 Direct & CF preferred domains

- **Direct access**: ingress domain or IP, port 443 by default; bind nodes or leave empty for global;
- **CF preferred domains**: Cloudflare preferred domain plus port, with a connectivity check;
- Both feed the “Access domain” candidates used by subscriptions and external-node rewriting (see 16.3).

### 8.2 CF IP pool

- Maintain preferred IP sources (including `bestproxy` style sources), fetch interval and ports;
- “Probe settings” control the probe interval, latency threshold and probe entry node; local probing
  only filters clearly unreachable IPs, while selecting an entry node simulates that node's line;
- When “Access domain” uses the CF IP pool without a concrete value, one entry (with its port) is
  picked at random.

### 8.3 WAF global rules

- Configure the WAF rule source URL and the rule files to sync;
- After syncing they are pushed to nodes and loaded by the node proxy (Nginx / Caddy);
- A file with a full URL is downloaded from that URL; otherwise “source URL + /file name” is used.

### 8.4 Rule files (routing rule files)

This tab only downloads rule files on the panel and pushes them to nodes; nothing takes effect
automatically. To use them in routing, reference them under “Protocol center → sing-box → Routing”
in Rule Sets and Rules (see 6.6).

- **Rule repositories**: enter `owner/repo` (GitHub, browsable) or a full download URL; scheduled
  sync can run every 6 / 12 hours, daily at 03:00, daily at midnight or weekly on Sunday;
- **Add file**: for single files outside a repository release (for example SagerNet `.srs` branch
  files); enter the full URL and it is downloaded automatically;
- **File list**: shows name, size, last update and the “Auto sync” switch, with per-file “Download”;
  the “Push to all nodes” button at the top pushes every rule file to all nodes;
- Files are downloaded into the panel's `data/rules/` and, once pushed, live under the node data
  directory's `rules/`; reference them in sing-box as `rules/<file name>`;
- Formats:
  - `.srs`: sing-box binary rule set, recommended and smallest;
  - `.json`: source-format rule set; `rule_set` must set `format: "source"`;
  - `.dat`: xray `geosite.dat` / `geoip.dat`, which sing-box cannot use directly.

> The collapsible “Usage” block at the top of the page contains reference examples, the xray mapping
> table and common errors.

## 9. Subscription center

The subscription center packages nodes into client-ready subscriptions: define subscription **formats** (what to emit, which rules, which plans can see them), then subscription **endpoints** (public domain / path), then hand the links out.

### 9.1 Subscription formats

“Subscription center” → “Subscription formats”; one row per client output:

| Field | Description |
|---|---|
| Name | Unique; `?config=<name>` matches on it and the customer dialog shows it |
| Client type | clash / shadowrocket / singbox / v2ray — display grouping only |
| Output format | `mihomo_yaml` (Clash/Mihomo), `singbox_json`, `xray_json`, `base64_uri`, `raw_uri` |
| Content-Type / extension | Response header and filename |
| Platform | win / mac / android / ios / universal; matched by `?platform=`, empty = universal |
| Bound plans | Empty = available to every plan; otherwise only those plans can use it |
| Rules | Per-format routing rules (structured editor for Mihomo, raw JSON per rule for sing-box / Xray). **Rules are not converted between formats** |

Notes:

- Several configs may exist for the same output format (e.g. `out`, `home`); pick one with `config=` in the link;
- Without `config`, the order is “config bound to the subscription → `platform` match → default”;
- A sing-box template may carry its own `route.rule_set` for clients, normally as `remote` so the
  client downloads it; local files pushed to a node's `rules/` under “Rule files” are only available
  to the core on that node, not to client subscriptions;
- sing-box / Xray configs must be created separately; if they don't exist they don't appear in customer links (see 10.3).

### 9.2 Subscription endpoints

“Subscription center” → “Subscription endpoints”; one row per public address:

| Field | Description |
|---|---|
| Domain | Public subscription domain |
| Path | Prefix under the domain, default `/` |
| Enabled | Disabled endpoints are ignored when building links |
| Description | Free-text note |

- **Multiple rows (multi-domain)** are supported; when several are enabled the provider domain follows the domain used by the current request (see 9.4);
- A dedicated subscription port serves at the root (`/<token>`, no `/sub`); when sharing the panel port it is `/sub/<token>`;
- Reverse proxies must forward `X-Forwarded-Proto` / `X-Forwarded-Host`, otherwise the first enabled endpoint is used. The panel's generated Caddy / Nginx site templates include both headers; hand-maintained proxy configs need them added manually.

### 9.3 Subscription links

Base form: `https://<sub-domain>/<token>` (panel port: `https://<panel-domain>/sub/<token>`)

| Parameter | Description |
|---|---|
| `format` | Output format; aliases: `clash` → mihomo_yaml, `singbox`/`sing-box` → singbox_json, `xray` → xray_json, `raw` → raw_uri, `base64`/`v2ray` → base64_uri |
| `config` | Apply a subscription format by name; must match `format`, otherwise ignored |
| `platform` | Match a config by platform (when `config` is omitted) |
| `providers` | `1` / `true`: Clash Provider mode (`proxy-providers` + `use`); default inlines nodes |

Examples:

```bash
# Clash dynamic subscription (config template + providers)
https://sub.example.com/<token>?format=clash&config=out&providers=1

# sing-box / Xray (only meaningful when such a config exists)
https://sub.example.com/<token>?format=singbox_json&config=sing-box-home
https://sub.example.com/<token>?format=xray_json&config=xray-home

# generic clients / plain text
https://sub.example.com/<token>?format=base64_uri
https://sub.example.com/<token>?format=raw_uri
```

### 9.4 Multi-domain and Provider mode

With `providers=1` every `proxy-providers` entry points back to the subscription endpoint. Domain selection:

1. **The domain this request used** (`X-Forwarded-Host` first value, port stripped, else `Host`) if it matches an **enabled** endpoint;
2. Otherwise the enabled endpoint with the **lowest ID**;
3. The path comes from that endpoint: `https://<domain><path>/<token>?format=mihomo_proxies_yaml...`.

So changing the domain needs no panel change: clients fetching via the new domain get the new domain inside providers, and an old domain left enabled is no longer hard-coded. If a client cached the old provider URL, update the subscription (or clear the provider cache / restart the client).

Additional notes:

- `proxy-providers` inside a shared format (`config_json`) is ignored (avoids cross-plan leakage); providers come from plan node groups and external sources;
- Internal and external provider cache paths are always derived from “internal provider defaults → cache path template” (default `./providers/{key}.yaml`); external sources cannot set their own;
- The legacy reserved provider `subscription-nodes` is no longer emitted: groups using "all nodes" expand to concrete providers, or inline nodes when the plan has none.

> short-lived reconnects, core restarts and counter resets do not clear them. Only after 60

## 26. FAQ

### 26.1 The panel does not start

- Check whether the port is already in use
- Check that `.env` is valid
- Check the logs: `journalctl -u corefusion -f`; without systemd, `tail -f <install-dir>/data/logs/panel.log`

### 26.2 Node offline

- Check that the Agent is running: `systemctl status corefusion-agent`
- Check network connectivity
- Check firewall rules (port `18443`)

### 26.3 Certificate issuance fails

- Check DNS resolution
- Check that port 80 is reachable
- Check the DNS provider configuration
- Check the certificate logs

### 26.4 Subscription does not work

- Check the subscription link
- Check that the node is online
- Check that the core process is running
- Check firewall rules

### 26.5 Recharge callback fails

- Check the callback URL
- Check that the site key matches
- Check the IP allow-list
- Check the order logs

### 26.6 Portal page is inaccessible

- Check that the portal port is open
- Check the portal path configuration
- **Important**: make sure the reverse proxy forwards the portal domain to the **portal engine port**, not the main panel port — forwarding to the wrong port shows a blank page or the panel instead of the portal. Check `upstream` / `local_port` in the proxy site record.
- Open `http://<portal-domain>:<portal-port>` directly to verify the portal engine itself
- Check the reverse proxy configuration
- Check the portal logs

## Appendix

### A. Default ports

| Port | Purpose |
|------|---------|
| Assigned by the setup wizard (random free port by default) | Admin panel (changeable) |
| 18443 | Agent gRPC (changeable) |
| 0 (disabled by default) | Dedicated subscription engine port (empty or `0` shares the main port) |
| 0 (disabled by default) | Dedicated portal engine port (empty or `0` shares the main port) |
| 80 / 443 | Reverse proxy (Caddy / Nginx) HTTP / HTTPS |

### B. Default paths

| Path | Purpose |
|------|---------|
| `/` | Admin panel (the portal also lives at `/` when no dedicated portal engine is configured) |
| `/sub/:token` | Subscription fetch (when no dedicated subscription port is configured) |
| `/p` | Portal page (when no dedicated portal port is configured) |
| `/:token` | Subscription fetch (with a dedicated subscription port, without the `/sub` prefix) |

### C. Command-line tool

The panel binary supports these subcommands (no arguments starts the server):

```bash
# Start the panel (same as ./corefusion server)
./corefusion

# Run database migrations
./corefusion migrate

# Non-interactive init / reset init state (see 3.4, 3.5)
./corefusion init --help
./corefusion reset-init

# Offline administration (when you cannot sign in)
./corefusion admin reset-password -u admin -p 'new-password'
./corefusion admin 2fa reset -u admin
./corefusion admin list

# Version / help
./corefusion version
./corefusion help
```

> With systemd, use `systemctl restart corefusion` and `journalctl -u corefusion -f`; without
> systemd (containers and similar), stop the old process and start it again with `nohup`, logs are
> in `data/logs/panel.log`.
